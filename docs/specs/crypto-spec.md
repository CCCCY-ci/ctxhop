---

## 1. 范围

**在范围内**：口令派生、密钥层级、Recovery Key、项目/会话标识的不可逆派生、对象加密格式、参数版本化。

**不在范围内**：同步编排、存储（remote 层只搬运不透明字节）、CLI 交互流程。

---

## 2. 这一层保护什么，不保护什么

沿用 PRD §10.1 的威胁模型。

**保护**：存储服务商读取内容；传输链路窃听；同一存储桶被他人读取；仅凭对象列表推断用户在做什么项目。

**不保护**：本机已被攻陷；用户自己的存储凭据泄露导致的数据删除；元数据侧信道（对象数量、大小、时间戳可推断活跃度）；用户同时丢失口令与 Recovery Key。

> 本层的失败模式与 adapter 层相反。adapter 猜错会**静默写坏数据**；加密错误通常是**响亮的**——解密失败、认证不通过。唯一安静的失败是"以为加密了其实没有"，因此测试必须显式断言写出的字节不含明文。

---

## 3. 密钥层级

```
passphrase ──Argon2id(salt, params)──> passphraseKEK ─┐
                                                      ├─> 解开 ─> dataKey (随机 32 字节)
recoveryKey ──HKDF──────────────────> recoveryKEK ───┘              │
                                                                    ├─HKDF("content")─> contentKey
                                                                    └─HKDF("identifier")─> idKey
```

### 3.1 为什么是两层而不是一层

最直接的设计是让口令直接派生出内容密钥。但那样**改口令就等于换密钥**，已有的全部密文瞬间失效，只能全量重新加密上传。

因此采用信封结构：`dataKey` 是一次性随机生成、此后永不改变的真正密钥；口令和 Recovery Key 各自包裹它一份。**改口令只需重新包裹 `dataKey`，已有密文完全不受影响。**

### 3.2 keyfile

包裹结果存放在远端一个固定键上，未加密（其中没有秘密）：

```
v1/keyfile
{
  "version": 1,
  "kdf": { "name": "argon2id", "salt": "...", "time": 3, "memoryKiB": 65536, "threads": 4 },
  "wrappedByPassphrase": "<AEAD(passphraseKEK, dataKey)>",
  "wrappedByRecoveryKey": "<AEAD(recoveryKEK, dataKey)>"
}
```

新设备只需：拉取 keyfile → 用口令（或 Recovery Key）解开 `dataKey` → 即可解密一切。**全程不需要任何已有设备在线**，这正是 PRD §5.1.1 那条核心卖点成立的原因。

---

## 4. KDF 选型

**Argon2id**，通过 `golang.org/x/crypto/argon2`。这是项目的第一个第三方依赖，代价已实测：

| 项 | 结果 |
|---|---|
| 直接依赖 | 1（`golang.org/x/crypto`，构建期另需 `x/sys`） |
| 二进制增量 | 约 180KB（1.6MB → 1.78MB） |
| 耗时（64MiB / t=3 / p=4） | 47ms |
| 耗时（256MiB / t=3 / p=4） | 195ms |
| cgo、交叉编译 | 不受影响，纯 Go |

**为什么不用标准库的 `crypto/pbkdf2`。** 它可用且零成本，但对 GPU 极其友好——同样的算力下猜测速率高出数个量级。口令是保护用户**全部会话数据**的唯一屏障，而威胁模型的核心场景就是密文落入他人之手后的离线爆破。为节省 180KB 在这一处降级，代价完全不成比例。

零依赖是**手段**（小体积、构建简单、供应链风险低），不是目的。`x/crypto` 由 Go 团队维护、纯 Go、不破坏 `CGO_ENABLED=0` 与一条命令交叉编译，是风险最低的一类依赖。

### 4.1 默认参数

`time=3`、`memory=64MiB`、`threads=4`、输出 32 字节。约 47ms，交互解锁无感。

参数记录在 keyfile 中，因此**将来可以调高而不破坏已有数据**：用旧参数解开 `dataKey`，用新参数重新包裹即可。

## 5. Recovery Key

### 5.1 形式

256 位随机值，Crockford Base32 编码（无 `I`/`L`/`O`/`U`，避免手抄歧义），每 4 字符一组，末尾附校验组：

```
AGSY-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-CCCC
```

要求：

* **必须能被抄在纸上**，因此排除易混字符，并强制分组。
* **必须能立刻发现抄错**：校验组覆盖全部内容，输入时先验校验再尝试解密，避免把"抄错一位"报成"口令错误"。
* 输入时大小写不敏感，连字符可有可无。

### 5.2 强制保存

PRD §10.2 要求首次设置时**强制引导保存，未完成不得进入正常使用流程**。文案不得让用户误以为存在找回途径——同时遗忘口令与 Recovery Key 时数据不可恢复，这是无服务端形态下唯一可行模型的代价。

### 5.3 Recovery Key 不经 Argon2id

它本身就是高熵随机值，不存在字典攻击面，用 HKDF 直接派生即可。对它做记忆硬化只会拖慢恢复流程，不增加任何安全性。

---

## 6. 标识派生

PRD §8.3 要求路径中的标识不可逆，否则**仅凭对象列表就能推断用户在做什么项目**——存储服务商无需解密任何内容即可看到"这个人有 40 个项目，其中一个叫 acme-payments"。

```
projectID = base32( HMAC-SHA256(idKey, "project\x00" + 规范化的 Git 远端地址)[:16] )
sessionID = base32( HMAC-SHA256(idKey, "session\x00" + projectID + "\x00" + 原生会话 ID)[:16] )
deviceID  = base32( HMAC-SHA256(idKey, "device\x00"  + 本机设备标识)[:16] )
```

要点：

* **域分隔符必须存在**（`"project\x00"` 等）。没有它，不同类型的输入可能碰撞出同一个标识。
* 128 位输出足以避免碰撞，且键长可控。
* 同一用户的不同设备**必须派生出相同的 projectID**，因此输入只能是跨设备稳定的值（规范化后的 Git 远端地址），不能掺入本机路径。

---

## 7. 对象加密格式

```
magic(4) = "ASx1" || version(1) || nonce(12) || ciphertext || tag(16)
```

* **AEAD 用 AES-256-GCM**（标准库）。
* **每个对象使用独立派生的密钥**：`objectKey = HKDF(contentKey, info = 对象的逻辑键路径)`。
* **AAD = 对象的逻辑键路径**。

### 7.1 为什么要绑定路径

若不把路径纳入 AAD，攻击者（或一个出错的同步逻辑）可以把 A 会话的分片**原样搬到** B 会话的位置，解密照样成功。绑定之后，密文只在它被写入的那个位置有效。

### 7.2 关于 nonce

分片不可变，看起来可以用确定性 nonce。但**元数据对象是会被重写的**，同一路径重复加密会导致 nonce 重用——对 GCM 而言是灾难性的（可恢复明文并伪造）。

因此：**一律使用随机 nonce 并写入头部**。配合每对象独立派生的密钥，即使随机 nonce 在不同对象间偶然相同也无害。

> 这条很容易在"优化"中被破坏。任何改成固定或计数器 nonce 的改动都必须先证明该对象永不重写。

### 7.3 篡改必须失败

密文任意一位被改动、tag 被改动、路径被改动，解密都必须失败并报错，**绝不返回部分明文**。

---

## 8. 绝不能做的事

1. **绝不把明文写向 remote**。任何交给存储层的字节必须已加密（P6）。
2. **绝不在日志、错误信息或诊断输出中出现**：口令、Recovery Key、任何密钥材料、明文片段。
3. **绝不在 nonce 可能重用的前提下加密**。
4. **绝不在认证失败时返回任何明文**。
5. **绝不把原生项目名或会话 ID 直接用作远端路径**。
6. 绝不为"方便"提供把密钥导出为明文的命令。
7. 密钥材料用完尽快清零，不得留在可被 GC 前长期持有的结构里。

---

## 9. 参数与格式版本化

keyfile 与对象头部各自带版本号。规则：

* 读取时遇到**更高的版本号一律拒绝**并提示升级，不得尝试猜测格式。
* KDF 参数可在解锁后透明升级（用旧参数解开、新参数重包裹）。
* 对象格式若变更，必须能同时读取旧版本，直到所有设备都已升级。

---

## 10. 测试计划

覆盖率目标 **95%+**（testing.md 对 `internal/crypto` 的要求）。

* **往返**：`Decrypt(Encrypt(x)) == x`，覆盖空输入、1 字节、大对象。
* **篡改**：密文、tag、nonce、版本字节各改一位，必须全部解密失败。
* **路径绑定**：用 A 的路径加密、用 B 的路径解密必须失败。
* **确定性标识**：同样输入必须产生同样的 ID；不同 `idKey` 必须产生不同 ID；域分隔有效（`project` 与 `session` 不碰撞）。
* **信封**：改口令后，旧密文仍可解密；旧口令失效；Recovery Key 仍可用。
* **Recovery Key**：编码往返；单字符抄错必须被校验捕获；大小写与连字符不敏感。
* **KDF 参数升级**：用旧参数写的 keyfile，升级后仍能解锁。
* **绝不明文**：加密任意输入后，断言输出字节中不含输入的任何可辨识片段。
* **模糊测试**：任意字节输入解密不得 panic。

## 12. 未决

1. 口令强度是否强制下限，以及是否提供"生成一个强口令"的选项。倾向提供生成器并给出强度提示，但不硬性拒绝——硬性规则会把用户推向"写在便利贴上"。
2. 元数据对象的重写频率若很高，是否需要为其单独设计版本号以避免竞争覆盖。
3. 密钥材料清零在 Go 中只能尽力而为（GC 可能已复制）。需明确这是尽力而为而非保证。

## 13. 实现中确定的事

### 13.1 `crypto/rand.Read` 永不失败

标准库明确保证：**`rand.Read` 从不返回错误**，系统熵源失败时它直接终止程序。因此原先在 `DefaultKDFParams`、`NewDataKey`、`NewRecoveryKey`、`Encrypt` 中对它的错误检查全是死代码，已删除，四个函数的签名随之简化。

这与 remote 层删掉 `filepath.Rel` 分支同理：**为覆盖率而活的死代码比没有更糟**。

### 13.2 失败的口令变更曾会损坏 keyfile

实现后测试抓到一个真缺陷：`ChangePassphrase` 先把新 salt 赋给 keyfile，再去包裹。包裹失败时 salt 已被替换，而 `WrappedByPassphrase` 仍是旧 salt 包的——**旧口令从此打不开，用户只剩 Recovery Key 一条路**。`ResetPassphrase` 与 `UpgradeKDF` 同病。

规则：**参数与包裹结果必须一起替换，或者一起保持原样**。实现为先在临时副本上完成包裹，成功后才写回。这与 adapter 写入路径的"全部校验通过之前不创建任何东西"是同一条原则。

### 13.3 KDF 参数必须校验

keyfile 存放在任何持有存储桶的人都能改写的位置。若不校验，攻击者把内存与时间开销改成 0，就能把对口令的离线爆破从昂贵变成瞬时。因此 `validate()` 设有下限，且**低于下限一律拒绝解锁**而非降级运行。
