## 1. 范围

**在范围内**：口令派生、密钥层级、Recovery Key、项目/会话标识的不可逆派生、对象加密格式、参数版本化。

**不在范围内**：同步编排、存储（remote 层只搬运不透明字节）、CLI 交互流程。

---

## 2. 这一层保护什么，不保护什么

沿用 PRD §10.1 的威胁模型。

**保护**：存储服务商读取内容；传输链路窃听；同一存储桶被他人读取；仅凭对象列表推断用户在做什么项目。

**不保护**：本机已被攻陷；用户自己的存储凭据泄露导致的数据删除；元数据侧信道（对象数量、大小、时间戳可推断活跃度）；用户同时丢失口令与 Recovery Key。

> 本层的失败模式与 adapter 层相反。adapter 猜错会**静默写坏数据**；加密错误通常是**响亮的**——解密失败、认证不通过。唯一安静的失败是"以为加密了其实没有"，因此测试必须显式断言写出的字节不含明文。

## 3. 密钥层级

```
passphrase ──Argon2id(salt, params)──> passphraseKEK ─┐
                                                      ├─> 解开 ─> masterKey (随机 32 字节)
recoveryKey ──HKDF──────────────────> recoveryKEK ───┘              │
                    ├─HKDF("identity-x25519")─> X25519 私钥 ─> 公钥
                    └─HKDF("identifier")──────> idKey
```

### 3.1 为什么是信封而不是直接派生

最直接的设计是让口令直接派生出内容密钥。但那样**改口令就等于换密钥**，已有的全部密文瞬间失效，只能全量重新加密上传。

因此采用信封结构：`masterKey` 是一次性随机生成、此后永不改变的真正秘密；口令和 Recovery Key 各自包裹它一份。**改口令只需重新包裹一次，已有密文完全不受影响。**

### 3.2 为什么信封本身仍是对称的

对象加密是非对称的（见 §3.3），但信封不能是——它要把**用户知道的东西**（口令、Recovery Key）变成打开它的密钥，而口令没有公钥这一半。因此 `wrap` / `unwrap` 是这一层唯一保留的对称加密。

### 3.3 为什么对象加密必须是非对称的

这一条不是密码学品味，是被产品形态逼出来的。

PRD §9.4 让 Agent 的 SessionEnd hook 调用 `agentsync push`。**hook 是非交互的——它要不到口令。** 于是推送必须只靠磁盘上已有的东西就能加密。

如果磁盘上放的是解开 `masterKey` 的对称密钥，那么"能读你 home 目录的人就能读你全部会话"，README 里那句 "The key ... cannot be recovered by anyone, including you" 也不再成立。

选择是把**推送与拉取的不对称性**直接写进密码学：

| | 推送（hook，无人值守） | 拉取 / 恢复（人的决定） |
|---|---|---|
| 需要 | 公钥（磁盘上，无害） | 口令 → X25519 私钥 |
| 能力 | 只能追加 | 能读 |

磁盘上唯一的秘密是 `idKey`，它只能算出远端路径，**解不开任何内容**。丢笔记本的后果因此从"全部会话泄露"降为"别人能往你的桶里追加垃圾"。

`idKey` 与私钥都由 `masterKey` 经 HKDF 派生，方向不可逆——持有 `idKey` 推不出 `masterKey`，也推不出私钥。

### 3.4 公钥必须本地固定（pin）

公钥存在 keyfile 里，而 keyfile 放在用户的存储里，**任何持有桶的人都能改写它**。

攻击者读不了任何东西，但如果他把公钥换成自己的，下一台加入的设备就会把它 pin 下来，**此后每一次推送都是加密给攻击者、且用户自己再也读不了**。注意这个攻击不需要攻破加密，只需要改一个公开字段。

因此：

1. 解锁时**必须**校验 keyfile 宣称的公钥确实是所包裹秘密的公钥一半，不符即拒绝（`ErrPublicKeyMismatch`）。
2. 设备只从**已通过口令解锁**的 keyfile 中取公钥来 pin——pin 的值必须是口令为之背书过的。
3. 错误信息必须明确让用户**不要推送**，因为推送才是交出数据的那个动作。

### 3.5 keyfile

包裹结果存放在远端一个固定键上，未加密（其中没有秘密）：

```
v1/keyfile
{
  "version": 1,
  "kdf": { "name": "argon2id", "salt": "...", "time": 3, "memoryKiB": 65536, "threads": 4 },
  "identityPublic": "<X25519 公钥，明文，因为它是公开的>",
  "wrappedByPassphrase": "<AEAD(passphraseKEK, masterKey)>",
  "wrappedByRecoveryKey": "<AEAD(recoveryKEK, masterKey)>"
}
```

新设备只需：拉取 keyfile → 用口令（或 Recovery Key）解开 → 即可解密一切。**全程不需要任何已有设备在线**，这正是 PRD §5.1.1 那条核心卖点成立的原因。

## 4. KDF 选型

**Argon2id**，通过 `golang.org/x/crypto/argon2`。这是项目的第一个第三方依赖，代价已实测：

| 项 | 结果 |
|---|---|
| 直接依赖 | 1（`golang.org/x/crypto`，构建期另需 `x/sys`） |
| 二进制增量 | 约 180KB（1.6MB → 1.78MB） |
| 耗时（64MiB / t=3 / p=4） | 47ms |
| 耗时（256MiB / t=3 / p=4） | 195ms |
| cgo、交叉编译 | 不受影响，纯 Go |

**为什么不用标准库的 `crypto/pbkdf2`。** 它可用且零成本，但对 GPU 极其友好——同样的算力下猜测速率高出数个量级。口令是保护用户**全部会话数据**的唯一屏障，而威胁模型的核心场景就是密文落入他人之手后的离线爆破。为节省 180KB 在这一处降级，代价完全不成比例。

零依赖是**手段**（小体积、构建简单、供应链风险低），不是目的。`x/crypto` 由 Go 团队维护、纯 Go、不破坏 `CGO_ENABLED=0` 与一条命令交叉编译，是风险最低的一类依赖。

### 4.1 默认参数

`time=3`、`memory=64MiB`、`threads=4`、输出 32 字节。约 47ms，交互解锁无感。

参数记录在 keyfile 中，因此**将来可以调高而不破坏已有数据**：用旧参数解开 `dataKey`，用新参数重新包裹即可。

## 5. Recovery Key

### 5.1 形式

256 位随机值，Crockford Base32 编码（无 `I`/`L`/`O`/`U`，避免手抄歧义），每 4 字符一组，末尾附校验组：

```
AGSY-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-CCCC
```

要求：

* **必须能被抄在纸上**，因此排除易混字符，并强制分组。
* **必须能立刻发现抄错**：校验组覆盖全部内容，输入时先验校验再尝试解密，避免把"抄错一位"报成"口令错误"。
* 输入时大小写不敏感，连字符可有可无。

### 5.2 强制保存

PRD §10.2 要求首次设置时**强制引导保存，未完成不得进入正常使用流程**。文案不得让用户误以为存在找回途径——同时遗忘口令与 Recovery Key 时数据不可恢复，这是无服务端形态下唯一可行模型的代价。

### 5.3 Recovery Key 不经 Argon2id

它本身就是高熵随机值，不存在字典攻击面，用 HKDF 直接派生即可。对它做记忆硬化只会拖慢恢复流程，不增加任何安全性。

---

## 6. 标识派生

PRD §8.3 要求路径中的标识不可逆，否则**仅凭对象列表就能推断用户在做什么项目**——存储服务商无需解密任何内容即可看到"这个人有 40 个项目，其中一个叫 acme-payments"。

```
projectID = base32( HMAC-SHA256(idKey, "project\x00" + 规范化的 Git 远端地址)[:16] )
sessionID = base32( HMAC-SHA256(idKey, "session\x00" + projectID + "\x00" + 原生会话 ID)[:16] )
deviceID  = base32( HMAC-SHA256(idKey, "device\x00"  + 本机设备标识)[:16] )
```

要点：

* **域分隔符必须存在**（`"project\x00"` 等）。没有它，不同类型的输入可能碰撞出同一个标识。
* 128 位输出足以避免碰撞，且键长可控。
* 同一用户的不同设备**必须派生出相同的 projectID**，因此输入只能是跨设备稳定的值（规范化后的 Git 远端地址），不能掺入本机路径。

## 7. 对象加密格式

```
magic(4) = "ASx1" || version(1) || 临时公钥(32) || nonce(12) || ciphertext || tag(16)
```

每次加密：

1. 生成一个**一次性的临时 X25519 密钥对**；
2. `shared = X25519(临时私钥, 收件人公钥)`；
3. `cek = HKDF-Expand(HKDF-Extract(salt = 临时公钥 ‖ 收件人公钥, shared), info = "agentsync/object " + 路径)`；
4. AES-256-GCM 加密，**AAD = 路径**；
5. 头部写入临时公钥，私钥即丢弃。

解密方用自己的私钥与头部的临时公钥做同样的交换，得到同一个 `cek`。

* **两个公钥都进 salt。** 不放收件人公钥，同一次交换就能被重放给另一个收件人。
* **角色显式传入，不靠猜。** 两侧必须构造出**逐字节相同**的 salt。一个"判断哪个私钥是临时的"的函数，离把两者弄反只有一次重构的距离——而弄反的表现是什么都解不开，且原因不可见。

### 7.1 为什么要绑定路径

若不把路径纳入密钥派生与 AAD，攻击者（或一个出错的同步逻辑）可以把 A 会话的分片**原样搬到** B 会话的位置，解密照样成功。绑定之后，密文只在它被写入的那个位置有效。

### 7.2 关于 nonce

每个对象都有自己的临时密钥对，因此 `cek` 天然逐对象唯一，nonce 用全零在理论上也是安全的。

仍然使用随机 nonce 并写入头部，代价是 12 字节：**万一将来某次改动缓存了临时密钥**（例如为了性能），随机 nonce 仍能避免同一密钥下的 nonce 重用——对 GCM 而言那是灾难性的（可恢复明文并伪造），不是"弱一点"。

> 任何改成固定或计数器 nonce 的改动，必须先证明临时密钥永不复用。

### 7.3 篡改必须失败

密文任意一位、tag、**临时公钥**、路径被改动，解密都必须失败并报错，**绝不返回部分明文**。

头部的临时公钥是攻击者可控的字节：它不是曲线上的可用点时，结论是"这个对象坏了"，而不是"你的密钥不对"。

## 8. 绝不能做的事

1. **绝不把明文写向 remote**。任何交给存储层的字节必须已加密（P6）。
2. **绝不在日志、错误信息或诊断输出中出现**：口令、Recovery Key、任何密钥材料、明文片段。
3. **绝不在 nonce 可能重用的前提下加密**。
4. **绝不在认证失败时返回任何明文**。
5. **绝不把原生项目名或会话 ID 直接用作远端路径**。
6. 绝不为"方便"提供把密钥导出为明文的命令。
7. 密钥材料用完尽快清零，不得留在可被 GC 前长期持有的结构里。

---

## 9. 参数与格式版本化

keyfile 与对象头部各自带版本号。规则：

* 读取时遇到**更高的版本号一律拒绝**并提示升级，不得尝试猜测格式。
* KDF 参数可在解锁后透明升级（用旧参数解开、新参数重包裹）。
* 对象格式若变更，必须能同时读取旧版本，直到所有设备都已升级。

## 10. 测试计划

覆盖率目标 **95%+**（testing.md 对 `internal/crypto` 的要求）。

* **往返**：`Decrypt(Encrypt(x)) == x`，覆盖空输入、1 字节、大对象。
* **篡改**：密文、tag、nonce、版本字节各改一位，必须全部解密失败。
* **路径绑定**：用 A 的路径加密、用 B 的路径解密必须失败。
* **确定性标识**：同样输入必须产生同样的 ID；不同 `idKey` 必须产生不同 ID；域分隔有效（`project` 与 `session` 不碰撞）。
* **信封**：改口令后，旧密文仍可解密；旧口令失效；Recovery Key 仍可用。
* **Recovery Key**：编码往返；单字符抄错必须被校验捕获；大小写与连字符不敏感。
* **KDF 参数升级**：用旧参数写的 keyfile，升级后仍能解锁。
* **绝不明文**：加密任意输入后，断言输出字节中不含输入的任何可辨识片段。
* **模糊测试**：任意字节输入解密不得 panic。

## 13. 实现中确定的事

### 13.1 `crypto/rand.Read` 永不失败

标准库明确保证：**`rand.Read` 从不返回错误**，系统熵源失败时它直接终止程序。因此原先在 `DefaultKDFParams`、`NewDataKey`、`NewRecoveryKey`、`Encrypt` 中对它的错误检查全是死代码，已删除，四个函数的签名随之简化。

这与 remote 层删掉 `filepath.Rel` 分支同理：**为覆盖率而活的死代码比没有更糟**。

### 13.2 失败的口令变更曾会损坏 keyfile

实现后测试抓到一个真缺陷：`ChangePassphrase` 先把新 salt 赋给 keyfile，再去包裹。包裹失败时 salt 已被替换，而 `WrappedByPassphrase` 仍是旧 salt 包的——**旧口令从此打不开，用户只剩 Recovery Key 一条路**。`ResetPassphrase` 与 `UpgradeKDF` 同病。

规则：**参数与包裹结果必须一起替换，或者一起保持原样**。实现为先在临时副本上完成包裹，成功后才写回。这与 adapter 写入路径的"全部校验通过之前不创建任何东西"是同一条原则。

### 13.3 KDF 参数必须校验

keyfile 存放在任何持有存储桶的人都能改写的位置。若不校验，攻击者把内存与时间开销改成 0，就能把对口令的离线爆破从昂贵变成瞬时。因此 `validate()` 设有下限，且**低于下限一律拒绝解锁**而非降级运行。

参数还必须有**上限**。Argon2id 面对荒谬参数的反应不是报错，而是照做：`memoryKiB = 4294967295` 会尝试约 4 TiB 分配，直接是不可恢复的运行时崩溃；`time = 4294967295` 则是一个没有 `context` 可取消的死循环。也就是说，只设下限时，改写 keyfile 的人虽拿不到明文，却能**让用户永久打不开自己的数据**。上限取 1 GiB / 16 轮 / 16 线程，远高于任何未来版本会选的默认值（当前是 64 MiB / 3 轮），提高默认值不会触发它。

### 13.4 `Close()` 必须让密钥不可用，而不只是清零

Review 抓到的最严重一条：`Close()` 只调 `zero(d.raw)`，切片长度仍是 32，于是 `derive` 的 `len(d.raw) != keyLen` 守卫照样放行。后果是**每一个被关闭的密钥都派生出同一个 content key**——32 个零字节的 HKDF，任何人离线可算。实测两个独立创建并关闭的 `DataKey` 都得到 `b1f0efe3…`。

一次 use-after-close 就会用这个公开常数加密用户的会话，**并且一路不报错**。这正是本包注释里写的唯一静默失败模式。修法是清零后 `d.raw = nil`：**清零保护的是内存快照，置空保护的是控制流**，两者缺一不可。

### 13.5 版本不匹配的两个方向必须分开

`Decrypt` 原先写的是 `v != objectVersion` 就返回 `ErrUnsupportedVersion`（"格式比本版本新"），于是**版本 0 也被报成"太新"**，用户会去追一个不存在的新版本。改为只有 `v > objectVersion` 才是"太新"，其余归入 `ErrCorrupt`。这同时给格式留出了余地——将来的版本 2 必须仍能读版本 1。

同理，unwrap 失败也不能一律归为"口令错误"。若 keyfile 由更新的版本写成，把它报成口令错误，用户的下一步就是重跑 `init` 覆盖 `v1/keyfile`，**把已上传的一切彻底变成孤儿**。`ErrUnsupportedVersion` 必须原样透出。

### 13.6 缺失的包裹要说自己缺失

`check()` 只要求两个包裹**至少有一个**存在。于是对一个没有口令包裹的 keyfile 调 `UnlockWithPassphrase`，会白跑一次完整的 Argon2id 派生，然后报"口令错误"——用户会反复重输一个永远不可能对的口令。各解锁路径必须检查自己真正需要的那个包裹，并指出另一条路可走。

### 13.7 域分隔的前提要么成立要么强制成立

`derive` 用 `\x00` 连接各部分，注释声称该字节"不可能出现在任何一部分里"。但 Go 字符串是可以含 NUL 的，这个声称比类型系统的保证更强。若不成立，`("a\x00b", "c")` 与 `("a", "b\x00c")` digest 相同，**两个不同的会话会共用一个远端路径**。

选择是让它成真而非把注释改软：含 NUL 的输入一律拒绝。**注释里的前提，能强制就强制，不能强制就别写成事实。**

### 13.8 `MarshalKeyfile` 必须拒绝空信封

`v1/keyfile` 是丢失即锁死用户全部历史的那一个对象，而调用方拿到结果的下一步就是覆盖写回远端。原先 `MarshalKeyfile` 对一个不含任何包裹的信封会照序列化不误，于是一个调用方的 bug 就等于不可恢复的数据丢失。现在它先过 `check()`——**在这里拒绝写入永远是安全的（BR-12）**。

### 13.9 "口令错了"与"文件坏了"必须分开

Review 修掉了"更新版本的 keyfile 被报成口令错误"，但只修了版本那一半。补测试时发现同一个错误还剩三种形态：**截断到 0 字节、截断到头部中间、包裹格式版本未知**——全都被 `translateUnwrapError` 归成了 `ErrWrongPassphrase`。

区分标准很清晰：

| 失败 | 判定时机 | 含义 |
|---|---|---|
| GCM 认证失败 | 用了密钥之后 | **二义**：口令错，或被篡改。AEAD 下无法区分，只能合报 |
| 太短 / magic 不对 / 版本未知 | **碰到密钥之前** | 关于字节的事实，与口令无关 |

因此只有认证失败才映射为"口令错误"，其余原样透出（`ErrDamagedKeyfile`）。

这个区分决定用户下一步去哪。被告知"口令错误"，他会重输、然后重跑 `init`——**而那会让已推送的全部会话变成孤儿**。

## 14. 覆盖率的结构上限

`testing.md §1` 要求本包 95%。实测 **92.7%**，且这个数字**不是靠补测试能提上去的**。

把未覆盖的语句逐条列出来后，29 条里约 22 条属于同一类：**标准库在固定长度输入下不可能失败的错误返回**。

```
aes.NewCipher(32 字节)        永不失败
cipher.NewGCM(AES block)      永不失败
hkdf.Extract / Expand(32 字节) 永不失败
ecdh.NewPrivateKey(32 字节)    X25519 下永不失败
ecdh.GenerateKey(rand.Reader)  与 rand.Read 同理，失败即崩溃
json.MarshalIndent(固定结构体)  永不失败
```

加上它们在调用链上的层层传递，约占本包语句的 6%——**上限约 94%**。

与 §13.1 的 `crypto/rand.Read` 不同，这些**删不掉**：Go 强制处理返回的 error，忽略它违反 code_style §2.1。非对称改造把这类调用又增加了一批（ECDH、Extract、公钥解析），这就是覆盖率从 95.4% 落到 92.7% 的全部原因。

按 `testing.md §1.0`，正确的动作是**说明缺口、而不是补测试凑数**。本包全部**可达**的失败路径都有测试覆盖，包括：错口令、错 Recovery Key、损坏的包裹、被替换的公钥、被搬动的分片、逐位篡改、逐字节截断、以及 fuzz。
