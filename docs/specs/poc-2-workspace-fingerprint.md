---

## 1. 要回答的问题

PRD §9.5 把一致性检查列为核心差异化能力，但它有一个隐含的失败模式：

> 误报率过高会导致用户直接忽略提示，使该能力完全失效。

所以 PoC-2 的问题不是"能不能检测到差异"，而是**"在用户改了一堆无关文件时，它会不会闭嘴"**。

---

## 2. 关键发现：会话自报的文件集不够用

用 `poc/touched` 分析两个真实会话：

| 会话 | 记录数 | tool_use | 带 `file_path` | 提取到的项目文件 |
|---|---|---|---|---|
| A（安装 skill） | 108 | 18 | 5 | 0（全部在项目外） |
| B（改后端+前端） | 566 | 121 | 41 | 15（11 写 4 读） |

提取本身是可靠的：会话 B 干净地还原出 15 个文件，读写分类正确。

**但缺口很大**。会话 B 的工具调用分布：

```
Bash          41   无 file_path
Grep          31   无 file_path
Read          21   有
Edit          18   有
PowerShell     8   无 file_path
Write          1   有
```

`Bash` 与 `PowerShell` 合计 49 次，占全部调用的 40%，且**完全不记录它们改了哪些文件**。而 shell 可以做任何事：`go build`、`npm install`、代码生成、格式化工具、`git checkout`。

结论：**只靠会话自报的 `file_path` 会漏掉相当比例的真实修改，且漏的方向是假阴性**——不该沉默的时候沉默，这是最危险的方向。

---

## 3. 设计修正：指纹以 Git 为锚，而不是以会话为锚

据此把指纹改为三层：

| 层 | 内容 | 作用 |
|---|---|---|
| **L1** | HEAD commit + 分支名 | 捕捉"你在另一份代码上" |
| **L2** | `git status --porcelain` 的脏文件集 | **捕捉一切修改，无论通过什么手段造成**，包括 shell |
| **L3** | 逐文件内容摘要，范围 = 会话触碰集 ∪ L2 脏文件集 | 精确定位，并把比对范围收窄以压制误报 |

L2 是补上 shell 缺口的关键：会话通过 Bash 改的文件如果未提交，会出现在脏文件集里；如果已提交，会被 L1 的 HEAD 比对捕捉。两者合起来闭合了这个洞。

会话触碰集不再是唯一数据源，而是**用来缩小比对范围**——这正是压制误报的机制。

## 4. 场景矩阵结果

`poc/fingerprint/scenarios.sh`，9 个场景全部通过：

| 场景 | 期望 | 结果 |
|---|---|---|
| 工作区无变化 | consistent | ✅ |
| **改了会话没碰过的文件** | **consistent** | ✅ |
| **一次性新增 5 个无关文件** | **consistent** | ✅ |
| 会话碰过的文件被改动 | inconsistent | ✅ |
| 会话的未提交改动被提交，之后又有新提交 | consistent | ✅ |
| 后续提交改动了会话碰过的文件 | explainable | ✅ |
| 会话碰过的文件被删除 | inconsistent | ✅ |
| 会话碰过的文件被格式化 | inconsistent | ✅ |
| 分支不包含会话起点 | inconsistent | ✅ |

加粗的三行是误报测试，也是这个功能成立与否的关键——**它们全部保持安静**。

### 4.1 两个值得记录的判定细节

**提交不改变内容。** 目标机器把会话的未提交改动提交掉之后，文件内容与指纹完全一致，因此判定为 consistent。这是理想结果：commit 本身不是差异。

**"可解释"仍然要显示文件清单。** 后续提交改动了会话碰过的文件时，差异虽然可解释，但 Agent 对该文件的认知依然是过时的。因此 explainable 一档也必须列出具体文件，不能只给一句"没问题"。

## 5. 开销

在一个真实仓库（454 个受控文件，`.git` 71MB）上：

| 操作 | 耗时 |
|---|---|
| capture | 0.199s |
| compare | 0.216s |
| 指纹体积 | 1316 字节 |

均在亚秒级，指纹体积可忽略不计，不构成同步负担。

## 6. 实现时必须避开的坑

PoC 过程中踩到一个会导致**假阴性**的真实缺陷，值得写进实现注意事项：

对 `git status --porcelain` 的输出做 `strings.TrimSpace` 会把**前导状态列**一起吃掉。`" M src/a.go"` 变成 `"M src/a.go"`，按固定偏移取路径就得到 `"rc/a.go"`，于是所有路径都匹配不上脏文件集，被改动的文件被静默归类为"可解释"。

正式实现应当解析 porcelain 输出而非按偏移切片，并对此写专门的测试。

---

## 7. 已知限制

1. **纯格式化改动会被判为不一致。** 内容确实变了，工具无法判断语义等价。属于可接受的误报，但如果用户普遍在目标机器上跑格式化工具，需要重新评估。
2. **非 Git 项目无法使用该检查。** L1、L2 都依赖 Git。非 Git 项目只能退化到 L3，效果显著变差。
3. **本次未验证超大仓库**（万级文件、GB 级工作区）的采集耗时。
4. **`git status` 在超大仓库上的耗时**未单独测量，可能成为主要开销来源。
5. 场景矩阵是构造出来的，不能替代真实使用中的误报率观察。
