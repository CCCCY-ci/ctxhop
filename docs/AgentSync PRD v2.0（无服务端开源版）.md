## 2. 产品背景

AI Coding Agent 已从辅助工具变为开发者的核心工作界面，人与 Agent 之间形成持续数小时至数天的长会话。一个完整 Session 包含需求、历史对话、代码分析、工具调用、终端输出、任务计划与 Agent 积累的上下文，重建成本随长度快速上升。

这些会话状态保存在本地设备。用户在设备 A 工作后切换到设备 B，即使两台设备使用同一账号、同一个 Git 仓库，也无法直接继续设备 A 上的会话。

开发者普遍同时使用公司电脑、个人电脑、笔记本，跨 Windows / macOS / Linux / WSL。Agent Session 与设备绑定，成为多设备工作流中最明显的断点。

现有解法——重新描述上下文、复制聊天记录、手抄上下文文档、手动拷贝 Session 文件、SSH 或远程桌面——要么重复劳动，要么要求源设备在线，都不构成真正的连续体验。

AgentSync 使 Agent Session 从"设备本地数据"变为"属于用户的可迁移开发上下文"。

## 3. 产品定位

AgentSync 是一个**开源的、无服务端的 AI Coding Agent 会话同步工具**。

它以单个命令行二进制的形式运行在用户本地，识别 Claude Code 等 Agent 产生的 Session，在本地完成加密后写入**用户自己的存储后端**（S3 兼容对象存储、网盘目录等），并在用户其他设备上按需恢复，使目标设备上的原生 Agent 能够识别并继续该会话。

AgentSync 不替代任何 Agent，不代理任何模型 API，不运行任何服务端，不接触用户的明文数据。

### 3.1 三条定位边界

**不做服务端。** 项目不运营任何存储或账号服务。所有数据流向用户自己配置的存储桶或目录。这既消除了运营成本，也从根本上消除了"服务方能否读取我的代码"这一信任问题——对隐私敏感的目标用户，这是决定性优势而非营销话术。

**不做 GUI。** 核心动作发生在终端：用户在设备 B 上正准备敲 `claude`。要求他切到图形界面点一下再切回来是负体验。MVP 只有 CLI。

**不做内容理解。** 不做 Session 摘要、搜索、跨 Agent 转换。产品只负责搬运的正确性。

### 3.2 与通用文件同步工具的差异

用户直接用 Syncthing / iCloud Drive / 网盘同步 Agent 的数据目录，是本产品最直接的免费替代方案。必须正面回答。

直接同步 Agent 目录会在四个层面**损坏**数据，而非仅仅体验略差：

1. **路径绑定**：Claude Code 的项目目录名由项目绝对路径编码而成，Session 内部同样记录工作目录。直接同步会在目标设备产生一个指向不存在路径的项目，Agent 无法识别。见 §9.3。
2. **冲突语义错误**：Session 是 Append-only 日志。文件同步工具在双端修改时采用 Last Write Wins 或产生 `conflict-copy` 文件——前者直接丢失一侧的完整对话，后者产生 Agent 无法识别的垃圾文件。见 §9.6。
3. **本地状态一致性**：部分 Agent 依赖常驻 SQLite 索引、WAL 文件与写入锁。在进程持有数据库时复制文件极易产生损坏。
4. **同步粒度过粗**：Agent 数据目录同时包含凭据、缓存、日志和 Session。整目录同步会把 API Key、Access Token 一并同步到其他设备。见 BR-07。

**关键区别在于：AgentSync 可以把文件同步工具当作传输层来用，但不把语义交给它。** §8.3 的存储布局保证任意两台设备永不写入同一个对象，因此即使跑在网盘目录上，存储层也没有机会做错事。

此外提供文件同步工具原理上无法提供的能力：工作区一致性检查（§9.5）、跨设备版本关系与分叉管理（§9.6）、Adapter 兼容性检测（§9.9）。

## 4. 设计原则

以下原则用于在后续所有设计争议中做判断，优先级从高到低。

### P1. 绝不损坏用户数据

宁可不同步，不可写坏。任何对 Agent 数据目录的写入必须是原子的；任何无法确认安全的操作一律中止并报错，而不是尝试修复。

### P2. 原生 Agent 优先

AgentSync 崩溃、卡死、配置错误、后端不可达时，用户使用 Claude Code 必须完全不受影响。AgentSync 是可选的旁路，不是必经路径。

### P3. 存储层是哑管道

不假设后端提供锁、事务、比较并交换或任何一致性保证。所有正确性由客户端逻辑保证。这使得后端可以是 S3、可以是网盘目录、可以是 U 盘。

### P4. 本地优先

所有操作先在本地完成并可离线工作。远端不可达时用户仍能正常使用 Agent 与本工具的本地功能，同步在后端恢复后继续。

### P5. 可退出

用户随时可以删除 AgentSync 及其配置，Agent 数据目录保持完全可用状态。不留残留、不改变 Agent 的原有行为。

### P6. 明文不出本机

任何离开本机的字节都必须已加密，包括 Session 正文、元数据、展示标题、路径信息与诊断数据。

### P7. 不收集任何数据

项目不采集任何形式的使用数据、统计信息或错误报告，不提供可选遥测，不内置任何上报通道。除用户自己配置的存储后端外，程序不主动向任何网络地址发起请求。

该原则不设例外。产品的度量方式必须在此前提下设计，见 §14。

## 5. 产品目标

### 5.1 核心目标

1. 用户能够在设备 A 产生 Claude Code Session，在设备 A 离线的情况下于设备 B 恢复并继续该会话。
2. 恢复过程不要求用户理解或手动操作 Agent 的本地 Session 文件。
3. 支持 Windows 与 macOS 之间的跨平台同步。
4. 支持同一项目在不同设备上使用不同本地路径。
5. 用户仅需配置一个存储后端与一个加密口令即可完成全部准备工作。
6. 所有数据在离开本机前完成加密，任何第三方（包括存储服务商）无法读取内容。
7. 目标设备工作区与 Session 记录状态不一致时，用户在继续会话前必然感知到差异。
8. 跨设备并发继续同一 Session 时，任一侧内容均不丢失。
9. AgentSync 的任何故障不影响 Claude Code 正常使用。

### 5.2 非目标

- 不运行任何服务端。
- 不提供账号体系。
- 不提供图形界面（MVP）。
- 不提供远程桌面、远程终端或远程控制。
- 不要求源设备在线。
- 不同步源代码，代码一致性由 Git 保证（但需检测并提示不一致）。
- 不代理任何模型 API。
- 不承诺 Codex 跨设备恢复，由 PoC 结果决定。
- 不承诺同一 Agent 跨大版本的 Session 兼容。
- 不支持跨 Agent 的 Session 转换。
- 不提供 Session 内容级摘要、搜索或分析。
- 不提供团队协作与多人共享。

## 6. 目标用户

### 6.1 核心用户

**高频 Agent 用户**：每天使用 Claude Code 完成开发任务，单 Session 上下文积累多，重建成本高。

**多设备开发者**：台式机 + 笔记本、公司电脑 + 个人电脑、Windows + macOS。

**多环境专业开发者**：Windows + WSL、macOS + Linux Server 等组合。

### 6.2 典型特征

- 日常主要在终端工作，习惯命令行完成操作；
- 熟悉 Git 和本地开发环境；
- 能够独立完成对象存储或网盘的基础配置；
- 对代码、终端输出、Session 数据隐私高度敏感，倾向自持数据；
- 对开源与自托管方案有明确偏好；
- 希望保持原生 Agent 体验，不愿改变既有工作方式。

### 6.3 用户前提

用户需要自行准备一个存储后端。这是无服务端形态的必然代价，也是本产品的用户筛选条件——愿意配置 S3 密钥的用户，恰好与在意数据自持的用户高度重合。

## 7. 核心场景

### 7.1 跨设备继续会话

用户白天在 Windows 台式机上用 Claude Code 开发。会话结束时 AgentSync 自动完成推送。

晚上打开 MacBook，进入同一个 Git 项目目录，执行 `agentsync resume`。工具列出该项目下可恢复的会话，用户选择最近一个，工具完成拉取、解密、路径改写与一致性检查。

用户执行 `claude --resume`，在原生会话列表中看到该会话并继续工作。

### 7.2 不同项目路径

Windows 上项目位于 `D:\Projects\Example`，macOS 上位于 `/Users/user/Projects/Example`。

AgentSync 通过 Git Remote 判定两者为同一项目，并在恢复时将 Session 中所有与源设备路径绑定的部分改写为目标设备的实际路径。

### 7.3 源设备离线

设备 A 已关机。用户在设备 B 上配置相同的存储后端与加密口令后，可获取设备 A 最后一次成功推送的全部会话，无需设备 A 参与任何授权流程。

### 7.4 恢复的会话与本地代码不一致

设备 A 上 Agent 修改了多个文件但未全部提交。用户在设备 B 恢复该会话时，Session 记录"已完成某些修改"，而设备 B 上的文件仍是旧版本。

AgentSync 在恢复前比对该会话**实际触碰过的文件**，明确列出差异并提示风险，避免 Agent 基于错误的世界模型继续工作。

此为 7.1 的常见结果，非边缘情况。

### 7.5 并发分叉

用户在设备 A 和设备 B 上分别从同一历史会话继续，产生两个后续分支。

AgentSync 检测到共同前缀与两个不同后缀，自动保留为两个独立会话并标注来源设备，不要求用户在两份已完成的工作之间做取舍。

### 7.6 首次在新设备启用

用户在新设备上安装二进制，执行 `agentsync init`，填入存储后端配置与加密口令，即完成全部准备。随后在任意项目目录执行 `agentsync resume` 即可工作。

## 8. 系统架构

无服务端形态下，架构本身就是产品的一部分，因此在 PRD 中定义。具体实现细节仍属技术设计范畴。

### 8.1 整体结构

```
┌─────────────────────────────────────────────┐
│  agentsync（单个 Go 二进制）                 │
│                                             │
│  CLI 命令层                                 │
│  ├─ 项目识别（Git）                          │
│  ├─ 工作区一致性检查                         │
│  └─ 同步编排（推送 / 拉取 / 分叉判定）        │
│                                             │
│  Adapter 层（每 Agent 一个实现）             │
│  ├─ 发现 Session                            │
│  ├─ 安全读取                                │
│  ├─ 路径改写                                │
│  └─ 原子写回                                │
│                                             │
│  加密层（口令派生密钥 · 对象级加密）          │
│                                             │
│  Remote 层（每后端一个 driver）              │
│  └─ List / Get / Put / Delete / Stat        │
└─────────────────────────────────────────────┘
        ↓ 加密后的对象
┌─────────────────────────────────────────────┐
│  用户自有存储                                │
│  S3 兼容 · 本地或挂载目录 · （后续）网盘 API  │
└─────────────────────────────────────────────┘
```

### 8.2 两个抽象层

产品的可扩展性完全由这两层决定，是架构设计的核心。

**Adapter 层**隔离第三方 Agent 的内部结构。新增一个 Agent 只需实现该接口，不触及同步逻辑。这是社区贡献 Gemini CLI、OpenCode 支持的入口。

**Remote 层**隔离存储后端。接口刻意保持最小（列举、读、写、删、元信息五个操作），不要求后端提供锁、事务或条件写入，以满足 P3。新增一个后端不触及任何业务逻辑。

### 8.3 存储布局

布局设计的唯一目标：**保证任意两台设备永不写入同一个对象**，使存储层不可能产生冲突。

```
<remote-root>/
  v1/
    projects/<project-id>/
      sessions/<session-id>/
        <device-id>/
          meta.age                 # 该设备对该会话的元数据
          000001.age               # 该设备写入的分片，单调递增
          000002.age
      project.age                  # 项目元信息
    devices/<device-id>.age        # 设备自述信息
```

关键约束：

- 每台设备只写 `<device-id>/` 下的对象，只读其他设备的对象。写路径不重叠，因此不存在并发写同一对象的可能。
- 分片一旦写入即不可变，只追加不修改。重传是幂等的。
- 会话的完整内容由客户端读取并按 §9.6 的规则合并各设备分片后得出。
- `project-id` 与 `session-id` 在路径中出现，必须为派生自密钥的不可逆标识（如以主密钥 HMAC 后取前若干字节），不得直接使用 Git Remote URL 或原生 Session ID，避免仅凭对象列表即可推断用户项目。

### 8.4 存储后端

**MVP 支持两类：**

| 后端 | 覆盖范围 | 优先级 |
|---|---|---|
| S3 兼容 | AWS S3、Cloudflare R2、Backblaze B2、MinIO、腾讯云 COS、阿里云 OSS、七牛等 | P0 |
| 本地/挂载目录 | 任意路径，配合 Syncthing、iCloud Drive、OneDrive、坚果云等使用；也用于测试 | P0 |

选择 S3 兼容作为首个云端 driver 的原因：**主流国内外对象存储几乎都提供 S3 兼容接口**，一个 driver 即可覆盖绝大多数用户，无需逐个对接。

本地目录 driver 的开发量极小，却带来两个价值：作为集成测试的基础设施，以及让不愿注册对象存储的用户可以直接把仓库放进已有网盘目录。

**后续版本考虑：** Google Drive、OneDrive、Dropbox 等需要 OAuth 的网盘 API，以及 WebDAV。

需要提前记录的问题：OAuth 类后端要求应用注册并分发 client secret，这对开源项目存在固有困难（secret 无法保密、用户可能需要自行注册应用），因此排在 S3 与目录后端之后，并在实现时单独评估方案。

### 8.5 触发方式

MVP **不实现常驻 daemon 与文件系统监听**。

Claude Code 提供会话生命周期 hook 机制。`agentsync init` 可为用户注册 hook，在会话结束时调用 `agentsync push`。相比文件监听，该方式：

- 触发时机准确，不需要 debounce 与"文件是否写完"的判断；
- 不产生常驻进程与内存占用；
- 不需要处理跨平台文件监听的差异与可靠性问题；
- 完全符合 P2 与 P5——用户删除 hook 即可完全退出。

同时提供 `agentsync push` 手动触发。常驻 watch 模式作为 P1，仅在 hook 机制不可用或用户明确需要时提供。

## 9. 功能需求

## 9.1 初始化与配置

### 需求说明

用户的全部准备工作应当是：安装二进制、执行一次 `agentsync init`、回答几个问题。

### 功能要求

- 交互式配置存储后端（类型、endpoint、bucket、凭据、路径前缀）。
- 配置完成后立即执行连通性与读写权限自检，失败时给出具体原因，不允许配置在错误状态下保存。
- 设置加密口令，并强制引导保存 Recovery Key（见 §10.2）。
- 生成本机设备标识与可读设备名（默认取主机名，可修改）。
- 检测已安装的 Agent 并询问是否注册同步 hook。
- 配置文件位置遵循各平台惯例，凭据不得以明文形式写入配置文件。
- 支持通过环境变量提供凭据，以适配 CI 或不愿落盘的用户。

### 优先级

P0。

---

## 9.2 Agent 检测与 Session 发现

### 功能要求

- 自动识别本机是否安装 Claude Code 及其版本。
- 定位其 Session 数据位置。
- 发现新建 Session 与已有 Session 的更新。
- 获取 Session 原生 ID、所属项目、创建与最后更新时间。
- 为 Session 生成展示标题（见 9.2.1）。
- 读取过程不得锁定或修改 Agent 的文件。
- 对 Agent 可能正在写入的 Session，必须保证读取到完整可解析的状态，不得上传截断的中间态。
- Agent 未安装时不报错，不影响其他功能。

### 9.2.1 展示标题

原生 Agent 通常不提供用户可读的会话名，仅有内部 ID。标题按以下优先级本地生成：

1. 用户手动设置的名称；
2. Agent 自身生成的摘要（若存在）；
3. 会话中第一条用户消息的截断文本；
4. 项目名 + 创建时间。

标题属于内容衍生数据，加密后随元数据同步。

### 优先级

P0。

---

## 9.3 项目识别与路径改写

### 需求说明

不同设备上的项目绝对路径不同，因此不得使用本地路径作为跨设备标识。同时，跨设备恢复不是文件搬运，而是一次结构转换。

Agent 的本地数据在多个层面与源设备的绝对路径绑定，至少包括：Session 所在的项目目录名本身可能由绝对路径编码而成、Session 内容中记录的工作目录、Session 内容中记录的文件路径、关联辅助数据中的路径引用。

### 项目识别规则

优先级依次为：

1. Git Remote（SSH 与 HTTPS 地址需标准化，`git@github.com:user/example.git` 与 `https://github.com/user/example.git` 必须识别为同一项目）；
2. Git 仓库的稳定标识；
3. 目录特征；
4. 用户手动绑定。

非 Git 目录默认不参与跨设备自动匹配，需用户手动绑定。

### 路径改写要求

- 将会话归属的项目目录标识改写为目标设备的实际路径形式。
- 改写会话内容中与项目根目录相关的路径引用。
- 处理 Windows 与 POSIX 的分隔符差异、大小写敏感性差异、非 ASCII 与含空格路径。
- 项目外的绝对路径引用保持原样，不做猜测性改写。
- 改写规则由 Adapter 定义并随 Adapter 版本管理。
- 改写全程在本地完成。
- 改写失败时不写入 Agent 目录，保留原始数据并报错。

### 验收重点

改写后的会话必须能被目标设备的原生 Agent 在正确项目下识别并继续，且不改变对话内容的语义。

### 优先级

P0。

---

## 9.4 推送

### 需求说明

将本地会话的新增内容加密后写入远端。

由于 Session 为 Append-only 结构，推送应为**增量追加**：只上传自上次推送以来新增的部分，作为新分片写入本设备目录。全量重传仅作为校验失败时的兜底。

### 功能要求

- 计算本地会话相对本设备上次推送位置的增量。
- 增量加密后写入新分片，分片不可变。
- 同时更新本设备的会话元数据对象。
- 远端不可达时将任务保留在本地队列，下次执行时继续。
- 支持失败重试与指数退避。
- 推送前应用 §10.4 的排除规则。
- 中断后重新执行必须是幂等的，不产生重复或损坏的分片。
- 明确输出本次推送的会话数、字节数与结果。

### 优先级

P0。

---

## 9.5 拉取与恢复

### 需求说明

远端元数据可以廉价地全量同步，但**会话正文按需拉取**。

一个活跃用户可能积累数百个会话。全量落盘会拖慢首次启用、污染 Agent 原生的会话选择列表、放大恢复失败的影响面，并带来无谓的解密与存储开销。

### 触发方式

- `agentsync resume`：在当前项目下交互选择会话并恢复；
- `agentsync resume <session>`：直接恢复指定会话；
- 可选配置"自动恢复某项目最近 N 个会话"，默认关闭。

### 恢复流程

1. 拉取该会话所有设备的分片并解密；
2. 按 §9.6 规则判定版本关系，必要时执行分叉处理；
3. 执行 §9.3 的路径改写；
4. 执行工作区一致性检查（见下）；
5. 用户确认后，原子写入 Agent 数据目录。

### 工作区一致性检查

这是本产品区别于任何文件同步方案的核心能力，属 P0。

**问题**：源设备上 Agent 修改的文件往往未提交到 Git。会话恢复到目标设备后，会话中记录的"文件已被修改"与目标设备磁盘上的实际内容可能完全不同。Agent 会基于错误的世界模型继续工作，产出错误且难以察觉的结果。这比无法恢复会话的损失更大。

**推送侧**：随会话记录轻量工作区指纹，分三层（该结构由 PoC-2 验证确定，见 `docs/specs/poc-2-workspace-fingerprint.md`）：

| 层 | 内容 | 作用 |
|---|---|---|
| L1 | 当前 Commit 与分支 | 捕捉"目标设备在另一份代码上" |
| L2 | Git 报告的脏文件集 | 捕捉一切修改，**无论通过什么手段造成** |
| L3 | 逐文件内容摘要，范围 = 会话触碰集 ∪ L2 | 精确定位差异 |

**指纹必须以 Git 状态为锚，而不是只依赖会话自报的文件。** PoC-2 实测显示，会话中约 40% 的工具调用是 shell 命令，它们不记录所改文件，而 shell 可以任意改动工作区。仅依赖会话自报会漏掉这些修改，且漏的方向是假阴性——不该沉默时沉默。L2 负责闭合这个缺口。

指纹只含路径与摘要，不含文件内容，不违反 BR-08。实测在 454 文件的仓库上采集耗时约 0.2 秒，指纹体积约 1.3KB。

**恢复侧**：比对目标设备当前状态与该指纹，区分三种结果——完全一致、可解释的差异（如目标设备已包含更新的提交）、不一致。

不一致时必须列出差异文件并说明风险。**"可解释的差异"同样必须列出具体文件**：差异虽有合理来源，但 Agent 对这些文件的认知依然是过时的。用户可选择继续、放弃或先同步代码。

**降低误报的关键设计**：内容比对的范围**限定为会话实际读写过的文件与推送时的脏文件**，而非整个工作区。用户在目标设备上改动的无关文件不产生任何提示。误报率过高会导致用户直接忽略提示，使该能力完全失效——这是本功能成败的关键。

**增强项（P1）**：用户确认继续时，在恢复的会话中注入一条说明性内容，告知 Agent 哪些文件的当前状态与会话记录不同，促使 Agent 重新读取而非依赖记忆。该行为可关闭，且不得破坏会话结构。

### 其他要求

- 不得覆盖目标设备上更新程度更高的会话。
- 恢复失败时保留原始数据并展示错误原因，不得留下半写入状态。

### 优先级

P0。

## 9.6 版本关系与分叉

### 需求说明

Agent Session 是 Append-only 事件日志，因此冲突的真实形态是"共同前缀 + 两个不同后缀"，而非两个不透明数据块的竞争。

由于会话天然支持从任意点分叉，同时保留两个分支的成本极低；而要求用户在两份已完成的工作之间二选一，决策成本高且伴随数据丢失风险。

因此默认策略是**自动 Fork**，而非阻塞用户做选择。

### 判定规则

- 本地是远端的严格前缀 → 本地落后，快进；
- 远端是本地的严格前缀 → 本地领先，正常推送；
- 存在共同前缀但后续内容不同 → 判定为分叉。

### 分叉处理

- 自动保留为两个独立会话，均含完整共同前缀，均可被原生 Agent 独立继续；
- 展示标题中标注来源设备与分叉时间；
- 向用户提示，但不阻塞同步流程；
- 用户可选择归档其中一个；被归档分支进入历史，不立即删除；
- 系统不得自动删除任何分支。

### 优先级

P0。

## 9.7 状态查询

### 状态定义

| 状态 | 说明 |
|---|---|
| 已同步 | 本地最新内容已成功推送 |
| 待推送 | 存在未推送的本地变更 |
| 仅远端 | 元数据已获取，正文尚未恢复到本机 |
| 落后 | 远端存在本机没有的后续内容 |
| 已分叉 | 该会话在不同设备产生了两个后续版本 |
| 推送失败 | 最近一次推送失败 |
| 已排除 | 命中排除规则，不参与同步 |

### 功能要求

`agentsync status` 在项目目录内展示该项目的会话状态，在项目外展示全局概览，并显示后端连通性与最近错误。

输出需同时适合人阅读与脚本解析（提供 `--json`）。

### 优先级

P0。

---

## 9.8 会话历史

远端分片不可变，天然形成历史。

### 功能要求

- 列出某会话的历史版本及其产生时间与设备；
- 恢复到指定历史版本，恢复前二次确认；
- 恢复操作产生新版本，不删除后续历史；
- 提供清理命令，按时间或数量裁剪远端历史。

### 优先级

P1。

## 9.9 Adapter 兼容性与诊断

### 兼容性分级

Agent 更新频繁。若采取"版本未知即完全停止"，产品将频繁停摆。因此采用**宽松读取、保守写入**的三级降级：

| 级别 | 条件 | 行为 |
|---|---|---|
| 完全兼容 | Adapter 已验证该 Agent 版本 | 正常推送与恢复 |
| 受限模式 | 版本未知，但会话结构可正常解析 | 继续推送与备份，恢复需用户显式确认 |
| 停止模式 | 结构无法解析或校验失败 | 停止该 Agent 的读写，保留已有数据，提示升级 |

版本兼容规则应尽量数据化，以便在不发布新二进制的情况下更新，缩短 Agent 更新后的不可用窗口。

### 诊断

`agentsync doctor` 输出：

- Agent 是否安装、版本、当前兼容级别及判定依据；
- Session 路径是否存在与可读写；
- 后端连通性与读写权限；
- 当前项目识别结果与映射状态；
- hook 注册状态；
- 排除规则命中情况；
- 最近错误。

输出不得包含会话正文、路径明文或任何凭据，以便用户直接粘贴到 issue 中。

### 优先级

P0（兼容性分级）。P1（诊断输出完整度）。

## 9.10 设备管理

### 功能要求

- 列出所有向该远端写入过的设备及其名称、系统、最后活动时间；
- 修改本机设备名；
- 移除某设备，即清理其在远端的数据目录。

### 已知限制

无服务端意味着无法撤销一台设备的访问权限——凭据与口令在用户手中，移除设备只能清理数据。若需要真正的访问撤销，用户须轮换存储后端凭据。该限制必须在文档中明确说明，不得含糊。

### 优先级

P1。

# 10. 安全与隐私

## 10.1 威胁模型

明确说明防护范围，避免过度承诺。

**防护：** 存储服务商读取用户内容；传输链路窃听；同一存储桶被他人读取时的内容泄露；对象列表泄露项目与会话信息（通过标识不可逆化缓解）。

**不防护：** 本机已被攻陷；用户自己的存储凭据泄露导致的数据删除或流量滥用（内容仍受加密保护）；元数据侧信道（对象数量、大小、时间戳可推断活跃度）；用户同时丢失口令与 Recovery Key。

## 10.2 加密

- 主密钥由用户口令通过抗暴力破解的 KDF 派生，口令与主密钥不写入任何文件、不上传。
- 所有上传对象使用带认证的加密算法，解密失败即视为损坏，不接受未经认证的数据。
- 元数据、展示标题、设备名同样加密。
- 路径中的项目与会话标识为密钥派生的不可逆值（§8.3）。
- 首次设置强制引导保存 Recovery Key，未完成保存不得进入正常使用流程。
- 支持修改口令；修改后 Recovery Key 需重新生成。

### 已知取舍

同时遗忘口令与 Recovery Key 时数据不可恢复。该取舍必须在设置流程中以不可跳过的方式告知，文案上不得让用户误以为存在找回途径。

无服务端形态下这是唯一可行的模型，也是"新设备恢复不需要旧设备在线"这一核心能力成立的前提。

具体算法在技术设计阶段确定。

## 10.3 不同步的数据

以下内容一律不参与同步，无论用户如何配置：

- Agent 的凭据与认证文件；
- Agent 的设备标识与安装标识；
- Agent 的缓存与日志；
- 源代码本身。

## 10.4 排除规则

加密解决"存储方能否读取"，但不解决"这份数据是否应该出现在另一台设备上"。

典型场景：公司电脑上的会话包含内网地址、内部服务凭据或受限代码，同步到个人设备可能违反公司政策，即使全程加密。

### 功能要求

- 项目级排除：指定项目完全不参与同步；
- 路径级排除：指定目录下的所有项目不参与同步；
- 设备级模式：某台设备可设为"只推不拉"或"完全不参与"；
- `agentsync status` 需清晰展示当前处于排除状态的项目；
- 排除在推送前生效，被排除内容不得离开本机。

### 优先级

P0。

## 10.5 数据删除

- 删除单个远端会话；
- 删除某项目的全部远端会话；
- 清空整个远端仓库。

删除命令必须明确区分"删除本机数据"与"删除远端数据"，避免本地清理导致远端数据被误删。删除远端数据需要显式确认。

# 11. 命令行设计

CLI 是产品的唯一界面，其设计质量等同于产品体验质量。

## 11.1 命令集

| 命令 | 说明 | 优先级 |
|---|---|---|
| `agentsync init` | 交互式初始化：后端、口令、设备名、hook 注册 | P0 |
| `agentsync status` | 当前项目或全局的同步状态，支持 `--json` | P0 |
| `agentsync list` | 列出当前项目可恢复的会话（标题、来源设备、时间） | P0 |
| `agentsync resume [session]` | 拉取、改写、检查、写入；不带参数时交互选择 | P0 |
| `agentsync push` | 推送本地变更，供 hook 与手动调用 | P0 |
| `agentsync doctor` | 诊断输出 | P0 |
| `agentsync project bind/unbind/list` | 项目绑定与排除管理 | P1 |
| `agentsync history <session>` | 会话历史版本 | P1 |
| `agentsync device list/rename/remove` | 设备管理 | P1 |
| `agentsync watch` | 常驻监听模式（hook 不可用时的兜底） | P1 |
| `agentsync stats` | 本机的跨设备恢复统计，见 §14 | P1 |

## 11.2 体验要求

- 所有命令在无网络时不得挂起，必须快速失败并给出可操作的错误信息。
- 所有破坏性操作需要显式确认，并支持 `--yes` 用于脚本。
- 输出遵循 Unix 惯例：正常结果到 stdout，诊断信息到 stderr，退出码有意义。
- 错误信息必须指出下一步该做什么，而不仅是描述失败。
- 支持 shell 补全。

## 11.3 目标体验

理想路径为两条命令：

```
agentsync resume      # 选择并恢复
claude --resume       # 在原生列表中继续
```

Claude Code 的会话即为已知目录下的文件，因此恢复后原生 Resume 列表可直接看到，无需任何 hack。这是该体验成立的前提，需在 PoC-1 中确认。

更进一步的自动化（如进入项目目录时自动拉取）留待后续版本。

# 12. 业务规则

**BR-01** 只同步用户主动启用的 Agent 与项目。

**BR-02** 用户可针对单个项目关闭同步，即使对应 Agent 全局开启。

**BR-03** 每台设备只写入自己的远端目录，永不修改其他设备写入的对象。

**BR-04** 远端分片一旦写入即不可变，只追加不修改。

**BR-05** 发生分叉时不得自动删除任何分支；默认同时保留，而非要求用户立即取舍。

**BR-06** AgentSync 的任何异常不得阻止用户直接使用原生 Agent。

**BR-07** 不同步整个 Agent 配置目录；凭据、认证信息、设备标识、缓存与日志一律排除。

**BR-08** 不同步源代码，但有义务检测并提示工作区不一致。

**BR-09** 命中排除规则的内容不得以任何形式离开本机，包括元数据与诊断输出。

**BR-10** 跨设备恢复必须经过路径改写；未完成改写的会话不得写入 Agent 目录。

**BR-11** 任何写入 Agent 数据目录的操作必须原子，中途失败不得留下部分写入状态。

**BR-12** 无法确认安全的操作一律中止并报错，不尝试自动修复。

**BR-13** 卸载 AgentSync 后，Agent 数据目录必须保持完全可用。

# 13. 异常场景

| 场景 | 处理 |
|---|---|
| 网络中断 | 本地保留待推送队列，下次执行继续，不阻塞用户 |
| 后端凭据失效 | 明确提示凭据问题及需要的权限，不重试到超时 |
| 后端权限不足 | `init` 阶段即检出；运行期检出时给出所需权限清单 |
| 后端存储满 | 停止推送，明确列出哪些会话未受保护，提供清理入口，不静默丢弃 |
| Agent 版本不兼容 | 按 §9.9 分级降级，提示当前级别与影响范围 |
| 会话文件损坏 | 不推送损坏内容，保留并提示；远端已有正常版本不受影响 |
| 本地项目不存在 | 元数据可展示，但在对应仓库建立前不写入 Agent 目录，提示先 Clone |
| 项目无法自动匹配 | 提示用户手动绑定本地目录 |
| 设备来回切换导致本地落后 | 先识别远端更新并快进；若本地已在旧版本上产生新内容，按 §9.6 分叉处理，不得覆盖 |
| 恢复过程中断 | 不得在 Agent 目录留下半写入状态；下次运行检测并清理 |
| 远端对象被外部删除 | 视为该分片丢失，明确报告受影响的会话，不静默跳过 |
| 口令遗忘 | 有可用设备时引导重设；无设备且 Recovery Key 丢失时明确告知不可恢复 |
| 多设备同时推送 | 由 §8.3 布局保证互不干扰，无需处理 |

# 14. 成功衡量

按 P7，产品**不采集任何数据**，不提供可选遥测，不内置上报通道。因此不存在 SaaS 意义上的使用度量，这是明确接受的取舍而非待解决的问题。

衡量只能依靠以下方式：

**本地自证（`agentsync stats`）**：在本机统计并展示"你已经完成了多少次跨设备恢复"。数据完全留在本地，任何时候都不上传。它的作用是让用户自己感知到价值——用户如果看到这个数字在涨，才会去推荐它。

**用户主动反馈**：issue、讨论区、以及用户自愿粘贴的 `agentsync stats` 与 `agentsync doctor` 输出。为此，这两个命令的输出必须默认就是可安全公开的（不含路径、项目名、内容）。

**社区信号**：GitHub star 与 issue 走势、issue 中反映的真实使用场景、用户是否自发添加新的 Adapter 或 Remote driver。

**核心问题不变**：

> 用户是否会因为这个工具的存在，自然地在多台设备之间继续同一个 AI Coding Session，而不再重新向 Agent 建立上下文？

如果用户只把它当作会话备份工具而极少发生跨设备恢复，说明需求强度不足，需重新评估定位。

# 15. MVP 验收标准

**跨设备恢复**：Windows 与 macOS 两台设备、项目绝对路径不同的前提下，设备 A 的 Claude Code 会话可在设备 B 恢复并通过原生 `claude --resume` 继续。源设备在恢复过程中无需在线。

**新设备启用**：仅持有存储后端配置与加密口令的用户，可在全新设备上独立完成安装、初始化与首次恢复，全程不需要任何已有设备参与。

**工作区一致性**：目标设备工作区与会话记录不一致时，用户在继续会话前必然看到明确提示；且在工作区仅有无关改动时不产生提示。

**安全**：所有离开本机的字节均已加密，包括元数据与标识；被排除的项目不产生任何出网数据。

**稳定性**：AgentSync 崩溃、后端不可达或配置错误时，Claude Code 完全不受影响；任何中断都不在 Agent 目录留下半写入状态。

**分叉**：双设备并发继续同一会话时不发生静默覆盖，两侧内容均可访问。

**可退出**：删除二进制与配置后，Agent 数据目录保持完全可用。

**存储后端**：S3 兼容与本地目录两个 driver 均通过完整测试矩阵。

# 17. 上线前必须完成的技术验证

## PoC-1：Claude Code 跨设备迁移（阻塞 MVP）

验证同一会话在两台设备、不同绝对路径、不同操作系统之间迁移后，能否通过原生 Resume 稳定继续。

需要明确：

1. 恢复一个会话所需的最小数据集；
2. 项目目录命名与绝对路径之间的编码规则；
3. 会话内部所有与路径绑定的字段；
4. 完整的路径改写规则，含 Windows/POSIX 差异、大小写敏感性、非 ASCII 与空格；
5. Agent 运行期间安全读取会话的方式；
6. 写入 Agent 目录的原子性保证方式；
7. 恢复后的会话是否直接出现在原生 Resume 列表中（§11.3 的前提）。

**该 PoC 不通过，产品不成立。应在写任何产品代码之前完成，语言不限，用最快的方式验证。**

## PoC-2：工作区一致性指纹（阻塞 MVP）

验证"仅检查会话触碰过的文件"这一范围限定能否在真实项目上给出准确判断，且在常见场景（未提交修改、分支不同、已被他人提交、文件被删除、文件被格式化工具改动）下不产生大量误报。

同时验证指纹采集在大型仓库上的耗时是否可接受。

误报率过高会使该能力失效，是本功能成败的关键。

## PoC-3：存储后端一致性（阻塞 MVP，工作量小）

验证 §8.3 的布局在 S3 兼容后端与网盘目录上均能正确工作，重点是最终一致性场景下的列举延迟、以及网盘客户端的部分同步状态是否会导致读到不完整对象。

## PoC-4：Codex 可移植性（不阻塞 MVP）

Codex 的本地状态除会话记录外还包含多个常驻 SQLite 数据库、活跃 WAL 与写入锁目录，并存在与设备绑定的安装标识与认证数据。恢复会话可能需要向正在被 Codex 进程使用的数据库写入，与 BR-06 存在结构性冲突。

需明确：哪些数据必须同步、哪些必须在目标设备重建、哪些不能直接复制、运行期写入是否可能安全实现。

在该 PoC 通过前，不得对外承诺 Codex 支持。

# 19. 风险

## 19.1 PoC-1 不通过

若 Claude Code 会话在结构上不可跨设备迁移，产品不成立。这是首要风险，必须最先验证。

## 19.2 第三方 Agent 结构变化

Agent 更新可能调整会话格式、目录结构或状态管理方式。通过 Adapter 隔离、兼容性分级与可数据化的版本规则压缩不可用窗口。该风险无法消除。

## 19.3 配置门槛导致流失

要求用户自备存储后端会在第一步筛掉相当比例的潜在用户。缓解手段是本地目录 driver（配合已有网盘零配置起步）与极其顺滑的 `init` 流程。

需要接受的事实：这个门槛是无服务端形态的必然代价，换来的是零成本运营与天然的信任优势。

## 19.4 通用文件同步工具作为免费替代

用户直接同步 Agent 目录是最直接的竞争方案。应对方式不是宣传，而是把 §3.2 的四类损坏做成用户可感知的能力差异，尤其是工作区一致性检查——这是文件同步工具原理上做不到的。

## 19.5 官方推出原生同步

Agent 厂商未来可能提供官方会话同步。因此产品不应长期定位为单一 Agent 的同步插件，而需持续建立跨 Agent、跨平台、统一管理的能力。开源形态下该风险的实际损失较小。

## 19.6 口令丢失导致数据不可恢复

采用口令派生密钥的直接代价。若在早期用户中高频发生将严重损害口碑。通过强制 Recovery Key 保存流程与清晰文案降低发生率。

## 19.7 无法度量真实使用

不收集任何数据意味着几乎无法判断产品是否真正被使用、在哪一步失败、成功率如何。这是 P7 的直接代价，且不打算通过任何技术手段缓解。

实际影响：产品决策将主要依赖用户主动反馈，而主动反馈天然偏向重度用户与遇到问题的用户，沉默的流失不可见。需要接受判断精度下降，并在设计上更依赖"把失败信息直接呈现给用户、让用户有动力来反馈"，而不是"我们自己观察到失败"。

# 20. 版本规划

## MVP

验证核心价值：跨设备原生 Resume 是否成立且好用。

范围：Windows + macOS、Claude Code、S3 兼容与本地目录后端、口令加密、增量推送与按需恢复、路径改写、工作区一致性检查、分叉自动 Fork、核心 CLI、hook 集成。

## V1

Linux 与 WSL；`watch` 常驻模式；会话历史管理；更多 CLI 能力；Adapter 接口稳定并对外开放；Google Drive / OneDrive / WebDAV 后端。

## V2

Gemini CLI、OpenCode 等更多 Agent（优先由社区贡献）；Codex（若 PoC-4 通过）；本地 Web UI；进入项目目录自动拉取等深度集成。

## 长期方向

在支持足够多 Agent 后，从"会话同步工具"演进为统一的 Agent Session 层，使开发者的工作上下文不依赖特定设备与特定 Agent 厂商。

**明确不在规划内**：官方托管后端。项目当前不提供、不规划任何托管服务。若未来出现明确且持续的用户需求，届时再单独评估——架构上它只是 Remote 层的又一个 driver，因此推迟该决定不产生任何技术债。在此之前，不应为"将来可能托管"而在设计中做任何妥协。
