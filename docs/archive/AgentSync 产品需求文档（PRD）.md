## 2. 产品背景

Claude Code、OpenAI Codex、Gemini CLI、OpenCode 等 AI Coding Agent 正逐渐从辅助工具转变为开发者日常工作流中的核心工具。开发者与 Agent 之间的交互也不再局限于简单的代码问答，而是逐渐形成持续数小时甚至数天的长会话。

一个完整的 Agent Session 通常包含用户需求、历史对话、代码分析结果、工具调用、终端执行结果、任务计划、文件修改信息以及 Agent 在当前任务中积累的上下文。随着 Session 长度增加，重新建立这些上下文的成本也随之提高。

目前主流 AI Coding Agent 的会话状态主要保存在本地设备。用户在设备 A 上完成了一部分开发工作后，如果切换到设备 B，即使两台设备使用相同账号并且拥有相同 Git Repository，也通常无法直接继续设备 A 上的本地 Session。

实际使用中，开发者往往同时使用公司电脑、个人电脑、笔记本、Windows、macOS、Linux 或 WSL 等多个开发环境。这导致 Agent Session 与具体设备绑定，成为多设备 AI 开发工作流中的明显断点。

现阶段用户通常通过重新向 Agent 描述上下文、复制聊天内容、编写上下文文档、手动复制 Session 文件、SSH 或远程桌面等方式解决这一问题。这些方式要么增加重复工作，要么要求原设备保持在线，都无法提供真正的跨设备连续使用体验。

AgentSync 希望解决这一问题，使 AI Coding Agent 的 Session 从"设备本地数据"转变为"属于用户的可迁移开发上下文"。

## 3. 产品定位

AgentSync 是一款面向 AI Coding Agent 的跨设备 Session 同步产品。

产品在用户本地识别 Claude Code、Codex 等 Agent 产生的 Session 数据，在本地完成必要的处理和加密后同步至云端，并在用户其他设备上按需恢复对应 Session，使目标设备上的原生 Agent 能够识别并继续该会话。

AgentSync 不替代 Claude Code、Codex 等 Agent，也不代理模型 API 请求。Agent 仍然由用户在本地原生运行，AgentSync 只负责 Session 的发现、同步、恢复和跨设备管理。

产品长期定位为：

**面向 AI Coding Agent 的跨平台、多 Agent Session 同步基础设施。**

### 3.1 与通用文件同步工具的差异

用户使用 Syncthing、iCloud Drive、Dropbox、OneDrive 等工具同步 Agent 的本地数据目录，是 AgentSync 最直接、成本最低的替代方案。产品定位必须明确回答这一问题，否则难以形成付费意愿。

通用文件同步工具在以下四点上会**损坏** Agent Session，而非仅仅是体验略差：

1. **路径绑定**：Claude Code 的项目目录名由项目绝对路径编码而成，Session 内部同样记录工作目录。直接同步会在目标设备产生一个指向不存在路径的项目，Agent 无法识别。跨设备恢复需要结构改写，见 8.6。
2. **冲突语义错误**：Agent Session 是 Append-only 日志。文件同步工具在双端修改时采用 Last Write Wins 或产生 `conflict-copy` 文件，前者直接丢失一侧的完整对话，后者产生 Agent 无法识别的垃圾文件。正确策略见 8.9。
3. **本地状态一致性**：部分 Agent 依赖本地 SQLite 索引、WAL 文件和写入锁。文件同步工具在进程持有数据库时复制文件，极易产生损坏或不一致的数据库。
4. **同步粒度过粗**：Agent 数据目录同时包含凭据、缓存、日志和 Session。整目录同步会把 API Key、Access Token 等凭据一并同步到其他设备，风险高于收益。见 BR-08 与 9.5。

此外，AgentSync 提供文件同步工具在原理上无法提供的能力：工作区一致性检查（8.7）、跨设备 Session 版本关系与冲突管理（8.9）、Adapter 兼容性检测（8.14）。

## 4. 产品目标

### 4.1 核心目标

MVP 阶段需要实现以下核心目标：

1. 用户能够在设备 A 创建 Claude Code Session，并在设备 A 离线后，在设备 B 恢复和继续该 Session。
2. Session 同步过程默认自动完成，不要求用户理解或操作 Agent 的本地 Session 文件。
3. 支持 Windows 与 macOS 之间的跨平台同步。
4. 支持同一个项目在不同设备上使用不同本地路径。
5. Session 在离开用户设备之前完成加密，云端服务不保存可直接读取的会话正文。
6. 在目标设备工作区与 Session 记录的状态不一致时，用户能够在继续会话之前感知到差异。
7. AgentSync 故障不得影响 Claude Code、Codex 本身的正常运行。
8. 对于跨设备同时继续同一 Session 的情况，系统能够识别分叉并保证任一侧的内容都不丢失。

### 4.2 非目标

MVP 阶段不包含以下能力：

- 不提供远程桌面、远程终端或远程控制能力。
- 不要求源设备保持在线。
- 不负责代码文件同步，代码版本管理仍由 Git 等工具完成（但 AgentSync 需要检测并提示不一致，见 8.7）。
- 不代理 Claude、OpenAI 或其他模型 API。
- 不提供 Cloud IDE 或云端代码运行环境。
- 不承诺 Codex 的完整跨设备恢复能力，该能力由 PoC 结果决定是否进入 V1。
- 不支持不同 Agent 之间直接转换原生 Session，例如 Claude Code Session 转换为 Codex Session。
- 不承诺同一 Agent 跨大版本的 Session 兼容，该行为由 Agent 厂商的迁移机制决定。
- 不提供团队协作和多人共享 Session。
- 不提供企业组织管理和 SSO。
- 不提供 Session 内容级智能总结、搜索或分析能力。

## 5. 目标用户

### 5.1 核心用户

AgentSync MVP 主要面向以下用户群体。

第一类是高频 AI Coding Agent 用户。这类用户已经大量使用 Claude Code、Codex 等工具完成开发任务，并且单个 Session 通常包含较多上下文，因此重新建立 Session 的成本较高。

第二类是多设备开发者，例如同时使用台式机与笔记本、公司电脑与个人电脑，或者同时使用 Windows 与 macOS 的开发者。

第三类是拥有多个开发环境的专业开发者，例如 Windows + WSL、macOS + Linux Server 等组合，希望在不同本地环境中延续相同 Agent 工作上下文。

### 5.2 典型用户特征

目标用户通常具备以下特征：

- 每天使用 Claude Code、Codex 或类似 Coding Agent；
- 单次 Agent Session 持续时间较长；
- 经常在两台及以上设备之间切换；
- 熟悉 Git 和本地开发环境；
- 日常主要在终端中工作，倾向使用命令行完成操作；
- 对代码、终端输出及 Session 数据隐私较为敏感；
- 希望尽量保持原生 Agent 使用体验，不愿改变已有工作方式。

## 6. 核心用户场景

### 6.1 跨设备继续 Claude Code Session

用户白天在 Windows 台式机上使用 Claude Code 开发某个项目。工作结束后，AgentSync 已自动完成当前 Session 的同步。

用户回家后打开 MacBook，并进入同一个 Git 项目。AgentSync 已经同步了该项目的 Session 列表，用户在 Session 列表中或通过 CLI 选择需要继续的 Session，AgentSync 将其恢复到本机。

用户启动 Claude Code 后，可以直接从之前的 Session 继续工作，而无需重新描述已经完成的内容。

### 6.2 不同项目路径下恢复 Session

用户在 Windows 上的项目路径为：

`D:\Projects\Example`

而 macOS 上的路径为：

`/Users/user/Projects/Example`

AgentSync 不应直接依赖绝对路径判断项目，而应结合 Git Remote、Repository 信息等建立统一项目标识，从而判断两个目录对应同一个项目。

恢复时，AgentSync 需要将 Session 中与源设备路径绑定的部分改写为目标设备的实际路径，使原生 Agent 能够正确识别该 Session 属于当前项目。

### 6.3 一台设备离线时继续工作

设备 A 完成 Session 同步后已经关机。

用户在设备 B 登录 AgentSync 后仍然可以获取设备 A 最后成功同步的 Session，不需要与设备 A 建立直接连接，也不需要设备 A 参与密钥授权。

### 6.4 恢复的 Session 与本地代码不一致

用户在设备 A 上让 Agent 修改了多个文件，但下班前并未全部提交到 Git。

用户在设备 B 上恢复该 Session。此时 Session 中记录了"已完成某些文件修改"，但设备 B 上对应文件仍然是较旧的版本。

AgentSync 在恢复前比对工作区状态，明确提示用户存在差异并列出差异文件，避免 Agent 在错误的代码状态上继续工作。

该场景是 6.1 的常见结果，而非边缘情况。

### 6.5 同一 Session 出现并发修改

用户在设备 A 和设备 B 上分别从同一个历史 Session 继续工作，并分别产生新的会话内容。

AgentSync 检测到两个设备均基于同一历史版本产生后续状态，不采用"最后写入覆盖"策略，而是将其自动分叉为两个独立 Session，并标注各自的来源设备，使用户不需要在两份工作之间做出取舍。

### 6.6 首次在第二台设备启用

用户已经在设备 A 使用 AgentSync 一段时间，现在在设备 B 首次安装。

用户登录账号并输入加密口令后，AgentSync 展示已有项目和 Session 列表，引导用户将其中至少一个项目绑定到设备 B 的本地目录，并完成第一次恢复。

该流程直接决定激活指标，见 15.2。

# 8. 功能需求

## 8.1 账号系统

### 需求说明

用户需要通过 AgentSync 账号建立自己的设备和 Session 同步空间。

MVP 支持邮箱或第三方 OAuth 登录。具体登录方式根据开发成本确定，但账号必须能够稳定识别同一用户的多个设备。

需要注意：账号登录仅用于身份识别和数据访问授权，不等同于获得 Session 解密能力。解密能力由 9.3 定义的加密口令体系单独提供。

### 功能要求

- 用户可以注册和登录 AgentSync。
- 登录状态应支持长期保持。
- 用户可以主动退出当前设备。
- 用户可以查看当前账号下已经登录的设备。
- 用户可以主动移除某一设备。
- 被移除设备不得继续获取新的 Session 数据。

### 优先级

P0。

---

## 8.2 多设备绑定与首次同步引导

### 需求说明

完成第二台设备绑定是产品的核心激活行为。如果用户在第二台设备上无法快速完成首次恢复，产品价值将完全无法体现。

该流程需要同时处理三件事：账号登录、加密口令验证、项目本地目录绑定。

### 功能要求

- 新设备登录后引导用户输入加密口令或使用 Recovery Key 恢复密钥。
- 展示账号下已有的项目列表及各项目的 Session 数量与最近活动时间。
- 引导用户将至少一个项目绑定到本机本地目录。
- 若本机不存在对应 Repository，提示用户先 Clone，并支持稍后再绑定。
- 绑定完成后引导用户完成第一次 Session 恢复。
- 整个流程不得要求已有设备在线。

### 验收重点

一名已有设备 A 数据的用户，在全新设备 B 上从安装到成功恢复第一个 Session，应能在无外部帮助的情况下独立完成。

### 优先级

P0。

---

## 8.3 Agent 自动检测

### 需求说明

AgentSync 安装完成后，应自动检测当前设备是否安装已支持的 AI Coding Agent。

MVP 支持 Claude Code。Codex 在 PoC 结论明确前，仅进行检测与只读的 Session 备份上传，不执行本地恢复写入。

### 功能要求

- 自动识别 Claude Code 是否已经安装。
- 识别对应 Agent 的版本信息。
- 识别对应 Agent 的 Session 数据位置。
- 用户可以单独开启或关闭某个 Agent 的同步。
- Agent 未安装时不应产生错误或影响其他 Agent。
- 检测结果需要与 8.14 的兼容性分级联动。

### 优先级

P0。

---

## 8.4 Session 自动发现

### 需求说明

AgentSync 应能够识别 Agent 新创建的 Session 以及已有 Session 的更新。

该能力应尽量基于文件系统监听、Agent 本地状态检测或 Adapter 机制实现，用户不需要改变启动 Claude Code 的方式。

### 功能要求

- 能够发现新的 Session。
- 能够识别已有 Session 的更新。
- 能够获取 Session 原生 ID。
- 能够识别 Session 所属项目。
- 能够记录 Session 的创建时间与最后更新时间。
- 能够为 Session 生成用于展示的标题，见 8.4.1。
- 同步过程不应锁定或破坏 Agent 正在使用的文件。
- 对于 Agent 正在写入的 Session，需要保证读取到的是完整可解析的状态，不得上传被截断的中间态。
- AgentSync 停止运行后，不得影响原生 Agent。

### 8.4.1 Session 展示标题

原生 Agent 通常不为 Session 提供用户可读名称，仅有内部 ID。AgentSync 需要自行生成展示用标题，规则优先级如下：

1. 用户手动设置的名称；
2. Agent 自身生成的摘要（若存在）；
3. Session 中第一条用户消息的截断文本；
4. 项目名 + 创建时间。

标题在本地生成，并作为 Session 元数据的一部分参与同步。标题属于会话内容衍生数据，同样需要加密，见 9.2。

### 优先级

P0。

---

## 8.5 项目识别与跨设备映射

### 需求说明

由于不同设备上的项目绝对路径通常不同，AgentSync 不得直接使用本地路径作为跨设备项目唯一标识。

系统需要建立 Logical Project Identity，将不同设备中的同一个 Repository 映射为同一个 AgentSync Project。

### 识别规则

默认优先使用以下信息：

1. Git Remote Repository；
2. Git Repository 的稳定标识；
3. 项目目录特征；
4. 用户手动确认。

对于 Git Remote，应对 SSH 和 HTTPS 地址进行标准化。例如以下地址需要被识别为同一个 Repository：

`git@github.com:user/example.git`

`https://github.com/user/example.git`

### 功能要求

- 自动识别 Git Repository。
- 自动进行跨设备项目匹配。
- 在无法可靠判断项目关系时要求用户确认。
- 用户可以手动修改项目映射。
- 用户可以关闭某个项目的 Session 同步。
- 支持非 Git 目录的项目，此类项目默认不参与跨设备匹配，需要用户手动绑定。

### 优先级

P0。

---

## 8.6 跨设备路径改写

### 需求说明

跨设备恢复 Session 不是文件搬运，而是一次结构转换。

Agent 的本地 Session 数据通常在多个层面与源设备的绝对路径绑定，至少包括：

- Session 文件所在的项目目录名本身可能由绝对路径编码而成；
- Session 内容中记录的工作目录；
- Session 内容中记录的文件路径；
- 与 Session 关联的本地辅助数据中的路径引用。

因此恢复过程必须完成从源设备路径空间到目标设备路径空间的映射，并同时处理 Windows 与 POSIX 之间的路径分隔符与大小写差异。

### 功能要求

- 恢复时将 Session 归属的项目目录标识改写为目标设备的实际路径形式。
- 改写 Session 内容中与项目根目录相关的路径引用。
- 保持项目外的绝对路径引用原样，不做猜测性改写。
- 改写全部在目标设备本地完成，不依赖服务端解密，不违反端到端加密约束。
- 改写规则由 Adapter 定义，并随 Adapter 版本管理。
- 改写失败时不写入 Agent 目录，保留原始数据并提示用户。

### 验收重点

改写后的 Session 必须能够被目标设备上的原生 Agent 在正确的项目下识别并继续。

改写不得破坏 Session 的可解析性，也不得改变对话内容的语义。

### 优先级

P0。

---

## 8.7 工作区一致性检查

### 需求说明

Session 同步成功不等于用户可以安全继续工作。

在真实场景中，源设备上的 Agent 往往修改了尚未提交到 Git 的文件。当 Session 被恢复到目标设备后，Session 中记录的"文件已被修改"与目标设备磁盘上的实际内容可能完全不同。

此时 Agent 会基于错误的世界模型继续工作，产出的结果既错误又难以被用户察觉。这比无法恢复 Session 造成的损失更大。

因此该能力属于 P0，而非增强功能。

### 功能要求

**上传侧：**

- 在上传 Session 时一并记录轻量的工作区指纹，至少包括：当前 Git Commit、当前分支、工作区是否干净、被 Session 修改过的文件清单及其内容摘要。
- 指纹只记录路径与摘要，不包含文件内容本身，因此不违反 BR-09。

**恢复侧：**

- 在恢复 Session 之前，比对目标设备当前工作区与该指纹的差异。
- 明确区分三种结果：完全一致、可解释的差异（例如目标设备已包含更新的提交）、不一致。
- 存在不一致时，在用户继续会话之前展示差异文件清单，并说明风险。
- 用户可以选择继续、放弃或先同步代码。

### 增强要求

在用户确认继续的情况下，AgentSync 可在恢复后的 Session 中注入一条说明性内容，告知 Agent 哪些文件的当前状态与会话记录不同，使 Agent 主动重新读取这些文件而非依赖记忆。

该注入行为需要用户可关闭，且必须以对 Agent 无害的形式实现，不得破坏 Session 结构。

### 优先级

P0（检查与提示）。P1（上下文注入）。

---

## 8.8 Session 上传与元数据同步

### 需求说明

当 Session 发生变化时，AgentSync 应自动将最新状态同步到云端。

同步不能对 Agent 本身产生明显性能影响，也不能因为频繁写入而持续上传大量重复数据。

同步分为两个层次：**元数据**在所有设备之间持续自动同步，**Session 正文**按 8.9 定义的策略处理。

### 元数据定义

元数据指用于在其他设备上展示与选择 Session 所需的最小信息，至少包括：Session ID、所属项目、所属 Agent、展示标题、创建与更新时间、来源设备、版本关系、当前同步状态、工作区指纹。

元数据同样属于用户内容的衍生数据，需要加密后上传。

### 功能要求

- 自动监听 Session 更新。
- 对连续高频更新执行合并或延迟上传。
- 默认在 Session 更新后短时间内完成同步。
- 网络不可用时保存本地待同步任务。
- 网络恢复后自动继续同步。
- 支持失败重试与指数退避。
- 客户端需要展示同步成功、同步中和同步失败状态。
- 上传前必须完成本地加密。
- 上传前必须应用 9.5 定义的排除规则。

### 性能要求

正常网络环境下，一次普通 Session 更新应在用户无明显感知的情况下完成。

考虑到 Agent Session 为 Append-only 结构，MVP 即应实现基于追加的增量上传，而非每次全量快照。全量快照仅作为结构变化或校验失败时的兜底手段。

### 优先级

P0。

---

## 8.9 Session 按需恢复

### 需求说明

当用户在其他设备上登录 AgentSync 后，该设备将自动获得全部 Session 的元数据，但不会自动将所有 Session 正文写入本地 Agent 目录。

原因在于：一个活跃用户可能积累数百个 Session，全量落盘会显著拖慢首次启用、污染 Agent 原生的 Session 选择列表、放大恢复失败的影响面，并增加不必要的存储与解密开销。

Session 正文仅在用户明确表达"要在这台设备继续这个 Session"时才拉取并恢复。

### 触发方式

- 在客户端 Session 列表中选择恢复；
- 通过 CLI 执行恢复，见 8.12；
- 用户可对指定项目开启"自动恢复最近 N 个 Session"，作为可选增强，默认关闭。

### 功能要求

- 自动、持续同步所有 Session 的元数据。
- 按需拉取指定 Session 的正文并解密。
- 判断本地 Session 与云端 Session 的版本关系。
- 执行 8.6 定义的路径改写。
- 执行 8.7 定义的工作区一致性检查。
- 恢复后的 Session 必须可以被原生 Agent 识别。
- 不得覆盖目标设备上更新程度更高的 Session。
- Session 恢复失败时保留原始数据并展示错误原因，不得留下半写入状态。
- 用户可以手动重新执行恢复。

### 验收重点

恢复后的 Claude Code Session 应能够通过 Claude Code 原生 Session Resume 能力继续。

恢复过程中源设备不需要在线。

### 优先级

P0。

---

## 8.10 同步状态

### 需求说明

用户需要能够快速判断当前 Session 是否已经安全同步，而不需要理解具体文件或底层技术。

### 状态定义

每个 Session 至少包含以下状态：

| 状态 | 说明 |
|---|---|
| 已同步 | 本地最新版本已经成功上传 |
| 同步中 | 当前存在上传或下载任务 |
| 待同步 | 当前离线或等待同步 |
| 同步失败 | 最近一次同步失败 |
| 仅云端 | 元数据已同步，正文尚未恢复到本机 |
| 已分叉 | 该 Session 在不同设备产生了两个后续版本 |
| 已暂停 | 用户关闭了该 Session 或项目的同步 |
| 已排除 | 命中排除规则，不参与同步 |

### 功能要求

客户端首页应展示整体同步状态，并允许用户查看具体 Agent、项目和 Session 的同步情况。

CLI 需要提供等价的状态查询能力。

### 优先级

P0。

---

## 8.11 Session 分叉与冲突管理

### 需求说明

同一 Session 可能在不同设备上分别被继续。

Agent Session 本质上是 Append-only 的事件日志，因此冲突的真实形态是"共同前缀 + 两个不同的后续分支"，而不是两个不透明数据块的竞争。

由于 Session 天然支持从任意点分叉，同时保留两个分支的成本极低，而要求用户在两份已完成的工作之间二选一的决策成本很高，且伴随数据丢失的风险。

因此 MVP 的默认策略是**自动 Fork**，而非阻塞用户做选择。

### 版本判定规则

- 若本地版本是云端版本的严格前缀，则本地落后，执行快进。
- 若云端版本是本地版本的严格前缀，则本地领先，正常上传。
- 若两者存在共同前缀但后续内容不同，则判定为分叉。

### 分叉处理

发生分叉后：

- 系统自动将两个分支保留为两个独立 Session；
- 两个 Session 均保留完整的共同前缀，均可被原生 Agent 独立继续；
- 在展示标题中标注来源设备与分叉时间，便于用户区分；
- 向用户发出通知，但不阻塞同步流程；
- 用户可以选择合并处理方式：保留两个、归档其中一个；
- 被归档的分支进入历史记录，而不是立即永久删除；
- 系统不得自动删除任何一个分支。

### 优先级

P0。

---

## 8.12 命令行工具

### 需求说明

目标用户主要在终端中工作。若恢复 Session 必须切换到 GUI 客户端操作，将显著削弱产品的顺手程度。

CLI 不是 GUI 的补充，而是主路径之一。

### 功能要求

MVP 至少提供：

- `agentsync status`：展示当前目录所属项目、本地与云端 Session 概览、同步状态与最近错误。
- `agentsync list`：列出当前项目的可恢复 Session，含标题、来源设备、更新时间。
- `agentsync resume [session]`：恢复指定 Session 到本机，包含路径改写与工作区一致性检查；不带参数时进入交互选择。
- `agentsync sync`：触发一次立即同步。
- `agentsync doctor`：输出 8.14 定义的诊断信息。

### 体验目标

理想终态是用户在设备 B 上直接使用 Agent 原生的 Resume 入口时，跨设备的 Session 已经可选。在该能力实现之前，CLI 是最接近原生体验的入口。

### 优先级

P0（`status`、`list`、`resume`）。P1（其余命令）。

---

## 8.13 Session 历史与恢复

### 需求说明

由于同步系统本身会形成 Session 的多个版本，产品应保留有限的历史状态，用于误覆盖、Session 损坏或同步异常时恢复。

### MVP 功能要求

- 展示 Session 最近同步版本。
- 展示版本产生时间和设备。
- 用户可以恢复到历史版本。
- 恢复历史版本前必须进行二次确认。
- 恢复操作本身产生新的版本，不直接删除后续历史。

### 优先级

P1。

---

## 8.14 同步诊断与 Adapter 兼容性

### 需求说明

由于产品依赖第三方 Agent 的本地 Session 结构，Agent 更新后可能导致兼容性问题，因此需要提供基础诊断能力与明确的降级策略。

### 兼容性分级

Agent 版本更新频繁，若采取"版本未知即完全停止"的策略，将导致产品频繁停摆。因此采用**宽松读取、保守写入**的三级降级：

| 级别 | 条件 | 行为 |
|---|---|---|
| 完全兼容 | Adapter 已验证该 Agent 版本 | 正常上传与恢复 |
| 受限模式 | Agent 版本未知，但 Session 结构可正常解析 | 继续上传与备份，暂停自动恢复写入，恢复需用户确认 |
| 停止模式 | Session 结构无法解析或校验失败 | 停止该 Agent 的读写，仅保留已有数据，提示用户升级 |

Adapter 的版本兼容规则必须支持在不发布新客户端版本的情况下更新，以缩短 Agent 更新后的不可用窗口。

### 诊断内容

诊断内容至少包括：

- Agent 是否安装；
- Agent 版本；
- 当前兼容性级别及判定依据；
- Session 路径是否存在；
- Session 路径是否可读写；
- 当前 AgentSync 是否能够识别 Session；
- 当前项目映射是否正常；
- 排除规则命中情况；
- 最近同步错误。

用户可以复制诊断结果用于反馈问题。诊断结果中不得包含 Session 正文或凭据信息。

### 优先级

P0（兼容性分级）。P1（诊断界面）。

用户可以查看：

- 设备名称；

- 客户端版本；

用户可以：

# 9. 安全与隐私要求

## 9.1 基本原则

Agent Session 中可能包含私有源代码、文件内容、Terminal 输出、数据库连接信息、API Key、Access Token、内部服务地址以及其他敏感信息，因此安全能力必须作为核心产品能力，而非后续增强功能。

安全需要覆盖两类风险：

1. **对服务端的风险**：云端不应能够读取用户会话内容，由 9.2、9.3 处理。
2. **跨设备扩散风险**：公司设备上的敏感信息不应被无差别同步到个人设备，由 9.5 处理。第二类风险无法通过加密解决，只能通过同步范围控制解决。

## 9.2 端到端加密

Session 数据必须在本地设备完成加密后才能上传。

Session 元数据与展示标题属于内容衍生数据，同样必须加密。

AgentSync 服务端不得依赖 Session 明文完成同步。

云端主要负责保存：

- 加密后的 Session 数据；
- 加密后的 Session 元数据；
- 同步所需的不可避免的明文最小集（对象大小、时间戳、版本关系等）；
- 设备信息；
- Session 版本关系。

## 9.3 密钥管理

### 方案定案

MVP 采用**用户加密口令派生密钥 + Recovery Key 兜底**的模型。

该选择由产品目标 4.1.1 直接决定：核心卖点要求源设备离线时新设备仍可恢复 Session。若采用设备互签授权模型，新设备入册需要已有设备在线批准，将与该卖点直接冲突。

### 功能要求

- 用户在首次使用时设置加密口令，主密钥由该口令派生，服务端不保存口令与主密钥。
- 首次设置时强制引导用户保存 Recovery Key，未完成保存不得进入正常使用流程。
- 新设备仅需账号登录 + 加密口令（或 Recovery Key）即可获得解密能力，全过程不要求任何已有设备在线。
- 用户可以修改加密口令，修改后 Recovery Key 需要重新生成。
- 用户移除设备后，该设备不能继续获得未来的数据密钥。

### 已知取舍

用户同时遗忘加密口令与 Recovery Key 时，云端数据不可恢复。

该取舍必须在设置流程中以明确、不可跳过的方式告知用户，并在文案上避免使用可能让用户误以为可通过客服找回的表述。

具体密码学算法在技术设计阶段确定，不在 PRD 中规定。

## 9.4 数据删除

用户需要能够：

- 删除单个云端 Session；
- 删除项目全部 Session；
- 删除 AgentSync 账号及相关云端数据。

删除操作需要明确区分"删除本机数据"和"删除云端及其他设备数据"，避免由于某台设备本地 Session 被清理导致所有设备数据被误删除。

## 9.5 同步范围控制与敏感数据排除

### 需求说明

端到端加密解决的是"服务端能否读取"，但无法解决"这份数据是否应该出现在另一台设备上"。

典型场景：用户在公司电脑上的 Session 包含内网地址、内部服务凭据或受限代码，这些内容被同步到个人 MacBook 可能违反公司政策，即使全程加密。

### 功能要求

- 支持项目级排除：指定项目完全不参与同步。
- 支持路径级排除：指定本地目录下的所有项目不参与同步。
- 支持将某台设备标记为"仅上传"或"不参与同步"。
- 客户端需要清晰展示当前哪些项目处于排除状态。
- 排除规则在上传前生效，被排除内容不得离开本地设备。

### 默认行为

MVP 默认同步全部已识别项目，排除规则由用户主动配置。

在 Onboarding 中需要主动提示用户该能力的存在。

### 优先级

P0。

# 11. 关键业务规则

### BR-01

AgentSync 只同步用户主动启用的 Agent。

### BR-02

用户可以针对单个项目关闭同步，即使对应 Agent 全局处于开启状态。

### BR-03

同一个 Session 的新版本只能追加在其直接祖先版本之上，不能覆盖从其他分支产生的新版本。

### BR-04

发生 Session 分叉时，系统不得自动删除任何一个分支。默认行为是同时保留两个分支，而不是要求用户立即做出取舍。

### BR-05

设备 A 不在线不得影响设备 B 使用已经上传成功的 Session，也不得影响设备 B 获得解密能力。

### BR-06

AgentSync 无法识别新 Agent 版本时，按 8.14 定义的三级降级处理，优先保证数据继续被备份，其次限制危险写入，最后才完全停止。不得因版本未知而直接停止全部功能。

### BR-07

AgentSync 的任何同步异常不得阻止用户直接使用原生 Claude Code 或 Codex。

### BR-08

AgentSync 默认只处理 Agent Session 及恢复 Session 所必需的相关数据，不同步整个 Agent 配置目录。凭据文件、认证信息、设备标识、缓存和日志一律不参与同步。

### BR-09

源代码不属于 AgentSync 的同步对象。项目代码一致性由用户自行通过 Git 等方式保证，但 AgentSync 有义务检测并提示不一致，见 8.7。

### BR-10

命中排除规则的内容不得以任何形式离开本地设备，包括元数据与诊断信息。

### BR-11

跨设备恢复必须经过路径改写。未完成改写的 Session 不得写入 Agent 目录。

### BR-12

任何写入 Agent 数据目录的操作必须是原子的，中途失败不得留下部分写入状态。

---

# 12. 异常场景

## 12.1 网络中断

本地继续记录 Session 变化，待网络恢复后继续同步，不提示阻塞性错误。

## 12.2 云端服务不可用

Agent 原生功能保持正常。AgentSync 将待同步任务保存在本地并自动重试。

## 12.3 Agent 版本更新导致不兼容

按 8.14 的兼容性分级降级处理，并提示用户当前所处级别与影响范围。

## 12.4 Session 文件损坏

不得用损坏版本覆盖云端最后一个正常版本。系统应保留异常版本并提示用户。

## 12.5 本地项目不存在

云端 Session 元数据可以保留并展示，但在目标设备对应 Repository 尚未建立之前，不自动写入 Agent 的项目 Session 目录。

用户 Clone 或绑定项目后再执行恢复。

## 12.6 Repository 无法自动匹配

提示用户从本机目录中选择对应项目进行绑定。

## 12.7 设备之间来回切换导致本地版本落后

用户在设备 B 恢复并继续 Session 后，又回到设备 A 继续同一 Session。此时设备 A 上的本地文件是落后版本。

系统需要在设备 A 上先识别到云端存在更新版本并执行快进，若设备 A 已在旧版本上产生新内容，则按 8.11 的分叉规则处理，不得直接覆盖。

该场景是多设备用户的高频路径，不属于边缘情况。

## 12.8 恢复过程中断

恢复过程中客户端崩溃或断电时，不得在 Agent 目录留下半写入的 Session。下次启动应检测并清理未完成的恢复操作。

## 12.9 存储配额耗尽

停止新的正文上传，但继续维护元数据与本地待同步队列，明确提示用户当前哪些 Session 未受保护，并提供清理或升级入口。不得静默丢弃数据。

## 12.10 加密口令遗忘

在用户仍有已登录设备的情况下，引导用户在该设备上重新设置口令。若无任何已登录设备且 Recovery Key 丢失，明确告知数据不可恢复，不提供虚假希望。

# 13. 性能要求

MVP 阶段要求：

- AgentSync 常驻进程对日常开发性能影响应尽可能低；
- 空闲状态下不进行高频目录扫描；
- Session 高频更新时应进行 Debounce，避免产生过多网络请求；
- 普通 Session 更新在正常网络条件下应快速完成同步；
- 大型 Session 上传不得阻塞 Agent 或 IDE；
- 元数据同步的流量开销应显著低于正文同步，使多项目用户在移动网络下仍可正常使用；
- 客户端异常退出后，下次启动能够恢复未完成同步任务。

具体 CPU、内存、网络流量目标由技术方案阶段根据 PoC 测试结果确定。

|---|---|---|
| Windows | Windows | Claude Code |
| Windows | macOS | Claude Code |
| macOS | Windows | Claude Code |
| macOS | macOS | Claude Code |

- 较旧版本到较新版本；

- 项目路径含空格、非 ASCII 字符；

- 源设备离线；
- 多设备同时在线；
- Session 正在运行过程中发生同步；
- 恢复时工作区存在未提交修改。

# 15. 数据指标

## 15.1 北极星指标

**Successful Cross-device Session Resume**

定义：用户在设备 A 创建或更新 Session 后，在另一台设备恢复该 Session，**并在恢复后 10 分钟内产生新的用户消息**的次数。

必须包含"产生新用户消息"这一条件，否则用户仅打开查看也会被计入，导致指标无法反映真实的工作延续行为。

该指标直接反映产品是否真正解决跨设备 Session 连续性问题。

## 15.2 核心指标

### 激活指标

- 完成第二台设备绑定的用户比例；
- 成功识别至少一个 Agent 的用户比例；
- 完成加密口令设置与 Recovery Key 保存的用户比例；
- 成功完成第一次 Session 同步的用户比例；
- 新设备从安装到首次成功恢复的耗时中位数。

### 使用指标

- 日均同步 Session 数量；
- 周均跨设备 Resume 次数；
- 使用两台及以上设备的活跃用户比例；
- 每用户平均同步项目数；
- 通过 CLI 触发恢复的比例（用于判断入口设计是否正确）。

### 价值验证指标

- 跨设备 Resume 后，用户手动补充上下文的字数（用于直接量化 4.1 所声称的价值）；
- 恢复时工作区一致性检查命中不一致的比例（用于验证 8.7 是否为真实问题）。

### 质量指标

- Session 上传成功率；
- Session 恢复成功率；
- Cross-device Resume 成功率；
- 路径改写失败率；
- Session 分叉发生率；
- 同步异常率；
- Adapter 兼容降级发生率及平均恢复时长。

### 留存指标

- 7 日留存；
- 30 日留存；
- 多设备用户 30 日留存；
- 完成过跨设备 Resume 用户的 30 日留存。

# 16. MVP 验收标准

MVP 是否可以进入公开测试，应以以下条件为核心判断标准。

### 跨设备恢复

在 Windows 和 macOS 任意两台设备之间，同一用户能够将设备 A 上的 Claude Code Session 同步到设备 B，并通过 Claude Code 原生能力继续该 Session。

两台设备的项目绝对路径不同。

源设备在恢复过程中不需要在线。

### 新设备启用

一名仅拥有账号与加密口令的用户，在全新设备上能够独立完成安装、登录、项目绑定与首次恢复，全程不需要任何已有设备在线。

### 工作区一致性

当目标设备的工作区与 Session 记录的状态不一致时，用户在继续会话之前必然会看到明确提示，不会在无感知的情况下让 Agent 基于错误的代码状态继续工作。

### 安全

所有 Session 正文与元数据在离开本地设备之前已经加密。

被排除的项目不产生任何出网数据。

### 稳定性

AgentSync 停止、崩溃、退出或云端不可用时，Claude Code 与 Codex 均可以继续正常使用。

任何异常中断都不会在 Agent 数据目录留下半写入状态。

### 分叉

双设备同时继续同一 Session 时，不发生静默数据覆盖或 Session 丢失，两侧内容均可继续访问。

### Codex

MVP 阶段仅需验证 Codex Session 能够被正确识别与备份上传，不要求实现跨设备恢复。

# 18. 产品依赖

AgentSync 的核心能力依赖 Claude Code、Codex 等第三方 Agent 的本地 Session 机制。

需要持续关注：

- Agent Session 文件结构；
- Session 存储路径与项目目录命名规则；
- Session ID 规则；
- Resume 机制；
- Agent 本地索引；
- Agent 数据库结构与并发写入协议；
- Agent 版本迁移机制；
- Session 中可能存在的设备或账号关联状态。

产品不应假设这些内部结构长期稳定，因此 Adapter 必须作为独立兼容层维护，且其兼容规则需要支持独立于客户端版本进行更新。

# 19. 核心风险

## 19.1 第三方 Agent 数据结构变化

Claude Code 或 Codex 更新后可能调整 Session 格式、目录结构或状态管理方式，导致同步或恢复失效。

产品需要通过 Adapter 版本管理、兼容性分级（8.14）和可热更新的兼容规则降低影响。该风险无法消除，只能压缩不可用窗口。

## 19.2 Codex Session 可移植性不足

初步观察表明，Codex 的本地状态除 Session 记录文件外，还包含多个常驻 SQLite 数据库、活跃的 WAL 文件以及写入锁目录，并存在与设备绑定的安装标识与认证数据。

这意味着恢复一个 Codex Session 可能需要向正在被 Codex 进程使用的数据库写入，与 BR-07（不得影响原生 Agent）存在结构性冲突。

这是将 Codex 移出 MVP 承诺范围的直接原因。在 PoC 给出明确结论前，不排除该能力在技术上不可安全实现的可能。

## 19.3 用户隐私信任

Agent Session 可能包含高度敏感的研发数据。若用户认为 AgentSync 服务端可以读取 Session 内容，将显著影响个人及企业开发者的采用意愿。

端到端加密需要作为产品默认能力，并在产品表达上做到可验证、可解释。

## 19.4 通用文件同步工具作为免费替代方案

相比官方推出原生同步，用户直接使用 Syncthing、iCloud Drive 等工具同步 Agent 目录是更近的替代方案，且免费。

该风险的应对方式不是宣传，而是把 3.1 中列出的四类损坏做成用户可感知的能力差异：正确的路径改写、正确的分叉语义、工作区一致性检查、选择性同步。

若产品无法在这些点上形成明显差异，则难以形成付费意愿。

## 19.5 官方推出原生同步功能

Anthropic、OpenAI 等厂商未来可能提供官方 Session Cloud Sync。

因此 AgentSync 不应长期定位为单一 Agent 的同步插件，而需要持续建立跨 Agent、跨平台、统一 Session 管理能力。

## 19.6 Agent 并发 Session 一致性

如果多个设备同时使用相同 Session，直接按照文件同步工具的方式处理可能造成会话损坏或数据覆盖。

因此需要在产品层定义 Session Version 与分叉语义，而不是简单使用文件的 Last Write Wins。

## 19.7 加密口令遗忘导致数据不可恢复

采用口令派生密钥模型的直接代价是用户可能永久丢失数据。

若该情况在早期用户中高频发生，将造成严重的口碑损害。需要通过强制 Recovery Key 保存流程、定期提醒和清晰文案降低发生率，并在指标中持续监控。

## 19.8 用户只把产品当作备份工具

若用户完成同步但极少发生跨设备 Resume，说明核心需求强度不足。

该风险由北极星指标直接监控，见 15.1 与第 23 节。

# 20. 商业模式假设

MVP 阶段优先验证使用需求和跨设备 Resume 频率，不急于验证复杂商业模式。

初步可采用 Freemium 模式。

### Free

适合体验和轻度用户，可以限制：

- 设备数量；
- 云端 Session 历史时间；
- 云端存储容量。

配额耗尽时的行为按 12.9 处理：停止新增正文上传但保留元数据与本地队列，明确提示，不静默丢弃数据。

### Pro

提供：

- 更多或无限设备；
- 更长 Session 历史；
- 更高存储额度；
- 高级 Session 恢复；
- BYOS；
- 更多 Agent 支持。

个人 Pro 定价需要保持在普通开发者工具可接受范围内，建议后续通过付费意愿测试确定。

### Team / Enterprise

长期可以围绕以下能力形成商业化：

- Team Workspace；
- Shared Session；
- Self-hosted；
- SSO；
- 企业策略；
- 审计；
- 自定义存储；
- 数据驻留控制。

9.5 的排除规则是企业版策略能力的雏形，但企业能力不进入 MVP。

# 21. 版本规划

## MVP

目标是验证"跨设备原生 Resume"这一核心价值是否成立。

范围包括 Windows、macOS、Claude Code、账号系统、加密口令体系、自动同步、项目映射与路径改写、工作区一致性检查、端到端加密、分叉处理、CLI 和基础状态展示。

Codex 在 MVP 中仅做识别与只读备份。

## V1

在 MVP 稳定后增加 Codex 完整恢复（若 PoC 通过）、Linux、WSL、Gemini CLI、OpenCode、Session 历史管理以及更完善的 Adapter 兼容体系。

## V2

增加 BYOS、Self-hosted、团队能力以及更完善的 Session 管理。

## 长期方向

在支持足够多 Agent 后，将 AgentSync 从单纯的 Session Sync 产品升级为统一的 Agent Session Layer，使开发者的 Agent 工作上下文不再依赖特定设备和特定 Agent 厂商。

# 22. 上线前必须完成的技术验证

在正式进入完整 MVP 开发前，必须完成以下 PoC。

### PoC-1：Claude Code 跨设备迁移（阻塞 MVP）

验证同一 Session 在两台不同设备、不同绝对项目路径和不同操作系统之间迁移后，是否能够通过 Claude Code 原生 Resume 功能稳定继续。

需要明确：

1. 恢复一个 Session 所需的最小数据集；
2. 项目目录命名与绝对路径之间的编码规则；
3. Session 内部所有与路径绑定的字段；
4. 路径改写的完整规则，含 Windows 与 POSIX 差异、大小写敏感性、非 ASCII 字符；
5. 在 Agent 进程运行期间安全读取 Session 的方式；
6. 写入 Agent 目录的原子性保证方式。

### PoC-2：工作区一致性指纹（阻塞 MVP）

验证在真实项目上采集工作区指纹的开销是否可接受，以及在常见场景（未提交修改、分支不同、已被他人提交、文件被删除）下能否给出准确且不产生大量误报的判断。

误报率过高会导致用户忽略提示，使该能力失效。

### PoC-3：Codex 可移植性（不阻塞 MVP）

验证 Codex Session 在不同设备之间迁移时的真实依赖，包括 Session 记录文件、本地 SQLite 状态、写入锁机制、安装标识与账号状态。

最终需要明确：

1. 哪些数据必须同步；
2. 哪些数据必须在目标设备重建；
3. 哪些数据不能直接复制；
4. 在 Codex 进程运行时写入其本地状态是否可能安全实现；
5. 同一个 OpenAI 账号不同设备之间的 Session 是否具备完整可移植性；
6. Codex 不同版本之间是否可以由官方机制自动完成 Session 迁移。

在 PoC-3 通过之前，不得对外承诺 Codex 的跨设备恢复能力。

# 23. 产品成功判断

AgentSync 的核心价值不是备份 Session，而是让用户真正能够在另一台设备继续工作。

因此 MVP 成功与否主要通过以下问题判断：

> 用户是否会因为 AgentSync 的存在，自然地在多台设备之间继续同一个 AI Coding Session，而不再需要重新向 Agent 建立上下文？

如果用户只将 AgentSync 当作 Session 备份工具，而很少发生跨设备 Resume，则说明产品核心需求强度不足，需要重新评估产品定位。

如果跨设备 Resume 成为高频行为，并明显减少用户重新建立上下文的成本，则证明产品方向成立。
